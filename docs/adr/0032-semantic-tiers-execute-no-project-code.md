# 0032. Semantic tiers execute no project code

## Status
Accepted 2026-10-13 (GM-513, owner decisions D1-D6). Experiments, the
per-server list of what a project could run and the options:
[`GM-513-semantic-servers-no-project-code.md`](../design/GM-513-semantic-servers-no-project-code.md).

## Context
Opening a project runs its semantic tier: rust-analyzer, pyright, or
`go/packages`. With the shipped configuration each of them executed
something the indexed project chose:

- **rust-analyzer** compiled and ran `build.rs` and loaded proc-macro dylibs;
  ran the `rustc`/wrappers `.cargo/config.toml` names (even with build
  scripts off); and, through the rustup proxies, ran a toolchain directory a
  `rust-toolchain.toml` `path =` names - including its own `rust-analyzer`
  as our server - or installed the `channel` it names.
- **pyright** ran `<root>/.venv/bin/python` (the plugin passed it as
  `python.pythonPath`), or `python3`/`python` from `PATH` when unset, with
  `cwd` = the project; and the plugin ran `<root>/node_modules/.bin/pyright`
  when pyright was not on `PATH`.
- **go/packages** ran no project file, but `GOTOOLCHAIN=auto` downloaded and
  ran the toolchain a `go.mod` names, and a `gopackagesdriver` on `PATH`
  replaced `go list`.

A cloned repository is untrusted input. Indexing it must not run its code.

## Decision
A semantic tier runs only the user's own binaries, configured by g-mesh.
Nothing the project's files name is executed.

- **D1 - rust-analyzer: build scripts and proc macros off, no opt-in.**
  `cargo.buildScripts.enable = false`, `procMacro.enable = false`,
  `checkOnSave = false` (`plugins/rust/plugin.toml`). rust-analyzer then builds
  nothing and writes no `target/`, so GM-524's D3 closes with no
  `cargo.targetDir`.
- **D2 - rust toolchain pinned to the user's rustup default.** The plugin
  runs every `rustup` call in its own directory, starts the absolute
  `rustup which --toolchain <default> rust-analyzer` (never a proxy), and
  gives the server `RUSTUP_TOOLCHAIN=<default>`, `RUSTC`/`CARGO_BUILD_RUSTC`/
  `CARGO` = that toolchain's binaries and the four `rustc` wrapper variables
  empty. Environment outranks `.cargo/config.toml` and `rust-toolchain.toml`.
  Without rustup, `RUSTC`/`CARGO` are the `PATH` ones and the wrappers are
  still emptied. The daemon's own `RUSTUP_TOOLCHAIN`, if set, is the pin.
  The same map sets `CARGO_ENCODED_RUSTFLAGS` empty: it outranks a project's
  `.cargo/config.toml` `[build]`/`[target.*]` `rustflags`, which otherwise
  reach the `rustc` probes of `cargo metadata` and can carry `-Z` flags such
  as `-Zcodegen-backend=<project dylib>`. Project-chosen `--cfg` flags in
  `rustflags` are not resolved, like the other project-chosen cfgs.
- **D3 - pyright runs no interpreter.** `python.pythonPath` is a path that
  cannot exist (a child of the plugin's executable file); pyright fails to
  run it and does not fall back to `PATH` (measured, pyright 1.1.414). The
  venv's `lib/python*/site-packages` (or `Lib/site-packages`), found by
  reading directories under `<root>/.venv` or `<root>/venv`, goes to
  `python.analysis.extraPaths`.
- **D4 - pyright is never taken from the project's `node_modules/.bin`,
  and never through `npx`.** Python resolves `PATH` only
  (`lsp::npm_candidates_on_path`). `npx --yes --package pyright`, run with
  the project as its cwd, executes the project's own `node_modules/pyright`
  (measured, npm 9.8.1: a directory holding only that package and its
  `.bin` links ran the project's script with no `pyright` on `PATH`), so it
  is the same channel as `node_modules/.bin`; it also reaches the registry
  the project's `.npmrc` names on every start (GM-512, D2: "Убрать npx для
  python, TS отдельно"). TypeScript keeps the project-local origin and `npx`
  until its own task.
- **D5 - Go cgo stays on.** It runs the user's `cc`/`pkg-config` with
  Go-allowlisted flags; those are not project binaries.
- **D6 - `go list` runs with `GOTOOLCHAIN=local` and
  `GOPACKAGESDRIVER=off`.**

Rejected: per-project opt-in for build scripts/proc macros (config plumbing,
a second rust-analyzer build per worktree, a second code path to test);
honouring an installed `rust-toolchain.toml` channel (two file formats, a
channel may lack the component); running the user's `PATH` interpreter for
pyright (still a binary run with `cwd` = project); dropping the TypeScript
origin here (outside this task's analysis).

## Consequences
- **Rust edges lost:** impls generated by third-party derives (`serde`,
  `thiserror`, `clap`, …), function-like macro output (`sqlx::query!`),
  `include!(concat!(env!("OUT_DIR"), …))` code, and code behind
  `cargo:rustc-cfg` cfgs. Built-in derives are unaffected; attribute-macro
  bodies resolve, their generated surroundings do not. A nightly- or
  MSRV-pinned project is analysed with the default toolchain's std.
- **Python edges lost:** what only a running interpreter knows - `.pth`
  `import` lines that compute paths, `sitecustomize` path changes, conda/pyenv
  layouts outside `lib/python*/site-packages`, the exact Python version.
  Plain `.pth` path lines (editable installs) still resolve.
- **Python users with pyright only inside the indexed project, or only
  reachable through `npx`,** get no semantic tier (structural stays) until
  they install it globally (`npm install -g pyright`); the resolution
  failure's log line says so.
- **Go:** a module whose `go` line is newer than the installed Go does not
  load; its pass degrades (logged) until the user upgrades Go.
- **Known residual, rust:** cargo applies a project's `.cargo/config.toml`
  `[env]` table to the `rustc` children of `cargo metadata`, so
  `DYLD_INSERT_LIBRARIES` (macOS) or `LD_PRELOAD` (Linux), with `force = true`
  if need be, loads a project-named library on first index. Empty parent
  values do not stop it and `force = true` overrides any parent value, so
  environment precedence cannot close this channel. It needs a prebuilt
  library committed to the repository. A follow-up backlog task tracks an
  OS-level sandbox for the server process.
- Faster rust-analyzer start; no `target/` under the project.
- Follow-ups: TypeScript's project-local server origin and its `npx`
  candidate (same exposure as python's had); no network and no writes
  under the root: [ADR 0033](0033-semantic-tiers-reach-no-network-and-write-nothing.md),
  whose rust setting joins the same env map.
