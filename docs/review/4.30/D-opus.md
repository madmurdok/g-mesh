## D-opus-1: The baseline walk excludes are defined twice in Rust and diverge in Go; move them into `g-mesh-walk`

- **Location:** `core/src/watcher/mod.rs:BASELINE_EXCLUDED_DIRS` (line 34), `plugins/sdk/src/walk.rs:BASELINE_EXCLUDED_DIRS` (line 50), `plugins/go/ignore.go:hardExcludedDirs` (line 47), `walk/src/lib.rs` (no such constant).
- **Problem:** duplication of a cross-process contract; misplaced ownership (cohesion). Which directories every walk skips is exactly the "which entries a walk reaches" question `g-mesh-walk` exists to answer ("The project walk g-mesh's plugins and core share"), yet the crate takes `excluded: &[String]` from callers and both its Rust callers hard-code `[".git", ".claude"]` with a comment that names the other copy. The Go plugin, which cannot link the crate, has `{".git"} + manifest` and **no `.claude`**: a structural drift already in the code.
- **Proposed change:** add `pub const BASELINE_EXCLUDED_DIRS` to `g-mesh-walk` and make `walk`/`walk_filtered`/`walk_dirs` always prune it (callers pass only their extra names). Core's `watcher` and the SDK's `walk` re-export it instead of declaring it. Add `.claude` to Go's `hardExcludedDirs` and pin the Go list against the Rust one through the shared fixture of D-opus-6 (or, short term, a Go test that reads `walk/src/lib.rs`'s constant the way `manifest_test.go` already reads `plugin.toml`).
- **Benefit:** a new always-excluded directory becomes one edit in one crate instead of three edits in three languages, and core and the plugins cannot disagree about which files exist.
- **Effort:** S. **Risk:** low; core's `ignore_layers.rs:105` checks the constant per path component and must keep importing it (re-export keeps the name).
- **Evidence:**
  - measured: `core/src/watcher/mod.rs:30-34` "same pair as `BASELINE_EXCLUDED_DIRS` in plugins/sdk/src/walk.rs ... `pub const BASELINE_EXCLUDED_DIRS: [&str; 2] = [".git", ".claude"];`"; `plugins/sdk/src/walk.rs:50` same literal. Both crates depend on `g-mesh-walk` (module-map 6.1).
  - measured: `plugins/go/ignore.go:45-53` "`hardExcludedDirs` is manifestExcludeDirs plus .git"; `grep -n claude plugins/go/*.go` (non-test) matches nothing; `plugins/go/walk.go:89` is the only name filter in the walk.
  - inferred: the Go bulk index therefore emits `File` nodes for `.go` files under `.claude/worktrees/`, which core's watcher (that does exclude `.claude`) never updates. `get_dependencies(core/src/project_walk.rs, Incoming)` shows `daemon/bulk_index` does not import core's walk, so core does not re-filter the plugin's file set (inferred from absence).

## D-opus-2: Four bundle scripts, three of them identical except for the language name

- **Location:** `scripts/bundle-plugin.sh` (TypeScript), `scripts/bundle-rust-plugin.sh`, `scripts/bundle-python-plugin.sh`, `scripts/bundle-go-plugin.sh`; dispatch in `scripts/build-targets.sh:205-211`.
- **Problem:** duplication. The three cargo-plugin bundlers differ only in the language string (plugin dir, binary name, log prefix, staged dir, manifest marker, handshake match). Each also carries a 30-60 line header arguing why it copies another's shape. A fix in staging, manifest rewriting or handshake smoke has to be made three times.
- **Proposed change:** one `scripts/bundle-cargo-plugin.sh <language> [target] [dest]` holding the shared body; `build-targets.sh` calls it for every crate-backed language and `bundle-go-plugin.sh` for Go (its build really is different: GOOS/GOARCH, no `.exe` from `go build`). Keep the old three names as two-line wrappers for one release if anything external calls them. `release.yml`'s `paths:` filter shrinks to two files.
- **Benefit:** adding a cargo-built language plugin needs no new bundler; staging/smoke fixes land once.
- **Effort:** S. **Risk:** low; `prepare-release-assets.sh` validates the output layout and `release.yml`'s `verify` job runs on PRs touching these scripts.
- **Evidence (measured):** `diff <(grep -v '^\s*#' bundle-python-plugin.sh) <(grep -v '^\s*#' bundle-rust-plugin.sh)` shows exactly 10 hunks, every one a language-name substitution (lines 6, 17, 31-32, 49, 59, 70, 75-79, 95-96, 99); the same diff between `bundle-plugin.sh` and `bundle-rust-plugin.sh` gives the same 10 hunks.

## D-opus-3: `core/build.rs` builds the Go plugin; dependency direction is inverted

- **Location:** `core/build.rs:main`, `core/build.rs` (Go build, lines 32-62), `core/go_plugin_build_flags.rs`.
- **Problem:** dependency direction. Core is the host and must not know how a particular plugin is built, but its build script runs `go build` in `../plugins/go` and tracks the Go sources with `rerun-if-changed`. Every core build is coupled to the Go toolchain's presence (a warning when absent) and to the Go plugin's file layout, and the build-flag constant has to be shared through `include!` with a core test and mirrored in `bundle-go-plugin.sh`.
- **Proposed change:** move the Go build into its own build-script-only workspace member (e.g. `plugins/go/build/` crate `g-mesh-plugin-go-build` with `build.rs` + empty `lib.rs`), so `cargo build --workspace` still produces `plugins/go/g-mesh-plugin-go` (the same contract core's tests already rely on for `g-mesh-fake-plugin`: "core's tests need the workspace built"). `GO_PLUGIN_BUILD_FLAGS` moves there; core's fingerprint test `include!`s it from the new path.
- **Benefit:** core can be built, and its build script changed, without the Go plugin; the Go plugin's build changes no longer invalidate core's build script.
- **Effort:** S. **Risk:** a `cargo build -p g-mesh` alone would stop building the Go binary; core tests that spawn Go (47 modules, see D-opus-8) would then need `--workspace`, which `scripts/test-deps.sh`/CI already use.
- **Evidence (measured):** `core/build.rs:1` "Keeps the Go plugin's binary (plugins/go/g-mesh-plugin-go) up to date"; `:37` `manifest_dir.join("../plugins/go")`; `core/go_plugin_build_flags.rs:1-4` "Included (with `include!`) by `core/build.rs` and by `core/tests/it/go_plugin_fingerprint.rs` ... `scripts/bundle-go-plugin.sh` passes the same flags".

## D-opus-4: Rust and Python plugins each re-implement the same id-dedup `Emitter` and tree-sitter `Positions` over the SDK builder

- **Location:** `plugins/rust/src/extractor/emit.rs:{Positions,Emitter}`, `plugins/python/src/extractor/emit.rs:{Positions,Emitter,render_target}`, `plugins/sdk/src/graph.rs:FileGraphBuilder::{add_node,add_edge}`; TS does the same job in `plugins/typescript/src/extractor/model.rs` ("nodes and edges by id").
- **Problem:** missing seam in the SDK; duplication. Both module docs say the same thing: the SDK builder lacks the "two things a ... extractor cannot do without - de-duplication by id and character columns". `FileGraphBuilder::add_node`/`add_edge` push unconditionally, so every plugin wraps it with its own `HashSet` of ids and its own byte->char `Positions` over `tree_sitter::Point`. The two `Emitter`s have the same method set (`new, positions, file_id, declare, placeholder, reexport, external_module, resolved_edge, placeholder_edge, import_edge, open_site, mark_syntax_errors, finish`) and the same four unit tests. Python additionally re-implements `render_target` claiming "the SDK keeps its renderer private", which is no longer true: the SDK exports it.
- **Proposed change:** (1) make `FileGraphBuilder` first-occurrence-wins by id (or add `FileGraphBuilder::dedup()` / a `DedupBuilder` wrapper) with `is_declared`; (2) add `Positions` to the SDK behind an optional `tree-sitter` feature (the SDK already owns `CharColumns`, which both `Positions::file_range` call); (3) delete Python's `render_target` and import `g_mesh_plugin_sdk::render_target`. Plugin `Emitter`s keep only language-specific additions (Python's overload `definitions`, deferred re-exports; Rust's hand-built `File` node).
- **Benefit:** the next tree-sitter plugin gets conformant emission for free; a change to dedup or column rules is one SDK change instead of 2-3 plugin changes. The test-only `census.rs` modules in Rust and Python (same `enable/push_ctx/pop_ctx/record/note_glob/start_file/end_file/with_data` skeleton, different enums) are a smaller candidate for the same move, generic over the reason/context enums.
- **Effort:** M. **Risk:** dedup in the builder changes behaviour for TS if it relies on duplicate pushes (inferred unlikely; TS dedups in its own model first); id-first-wins must keep source order, which the existing four emitter tests pin and can move to the SDK.
- **Evidence (measured):** `rust/src/extractor/emit.rs:1-3` and `python/src/extractor/emit.rs:1-3` identical opening ("adds the two things a ... extractor cannot do without - **de-duplication by id** and **character columns**"); `rust/.../emit.rs:181-188` `if self.nodes.insert(id.clone()) { self.graph.add_node(spec); ... }`; `sdk/src/graph.rs:486-511` `add_node` pushes with no check; `diff` of the `Positions` blocks (rust 55-140 vs python 88-178) differs only in doc text; `python/src/extractor/emit.rs:431-437` "Reproduced here rather than imported because the SDK keeps its renderer private" vs `plugins/sdk/src/lib.rs:102-103` `pub use graph::{placeholder_id, render_target, ...}`.

## D-opus-5: One plugin registry for scripts and workflows instead of ~12 hand-kept language lists

- **Location:** `scripts/build-targets.sh:BUNDLED_PLUGINS` (130), its `case` at 207-210 and per-language smoke at 371-380; `scripts/cut-release.sh:CRATE_BACKED_PLUGINS` (296-300); `scripts/test-sections.sh` (50, 100, 113, 125); `scripts/test-select.sh` (181, 236); `scripts/test-plugin-spawns.sh` (55, 194); `.github/workflows/release.yml` (187-190, 585, 791, 822); `.github/workflows/ci.yml` (one `tests: plugin-<lang>` step each, 827-843); core `languages::CATALOGUE` (named in the `BUNDLED_PLUGINS` comment).
- **Problem:** config sprawl. The set of plugins, and per plugin "cargo-built or Go", is restated in each script and workflow, sometimes in different orders (`typescript go rust python` vs `typescript rust python go`). `prepare-release-assets.sh` already shows the right pattern (it reads `build-targets.sh --plugins`) but nothing else does.
- **Proposed change:** make `plugins/*/plugin.toml` (plus one `kind = cargo|go` fact, or derive it from the presence of `Cargo.toml`) the registry, exposed by one helper `scripts/lib/plugins.sh` (`plugins_all`, `plugins_cargo`). `build-targets.sh`, `cut-release.sh`, `test-sections.sh`, `test-select.sh`, `test-plugin-spawns.sh` iterate it; `build-targets.sh`'s smoke becomes a loop over the list; `release.yml`'s PowerShell loops read `build-targets.sh --plugins`. For `ci.yml`, keep one step per section if the per-section UI is wanted, but add to `test-sections.sh check` an assertion that every section has a `tests: <section>` step in `ci.yml` (today nothing checks this; a new section missing from `ci.yml` silently does not run in CI).
- **Benefit:** adding, renaming or dropping a language plugin becomes a plugin-directory change plus a CI step, not a sweep across 8 files.
- **Effort:** M. **Risk:** shell portability (bash 3.2 on macOS runners, PowerShell in release.yml); per-language special cases (TS `.exe` existence check in the smoke, Go's separate version rule) must stay explicit.
- **Evidence (measured):** grep listing above; `scripts/build-targets.sh:125-130` "It must name the same languages as core's `languages::CATALOGUE`" (a fourth list kept by comment); `scripts/prepare-release-assets.sh:149-154` reads `build-targets.sh --plugins`; `grep -n ci.yml scripts/test-sections*.sh scripts/test-sections-check.py scripts/test-select.sh` matches nothing, so no script checks `ci.yml` against the section list.

## D-opus-6: Cross-language contracts with the Go plugin are held by prose mirrors; extend the shared-fixture pattern

- **Location:** `plugins/go/wire.go` (wire v2 mirror), `plugins/go/ids.go` (id hashing), `plugins/go/{walk,ignore,symlinks}.go` (walk + hand-rolled gitignore), `plugins/go/generated.go` (already shared); Rust counterparts `wire/src/lib.rs`, `plugins/sdk/src/ids.rs`, `walk/src/lib.rs` + `plugins/sdk/src/walk.rs`, `plugins/sdk/src/generated.rs`.
- **Problem:** duplication across a language boundary without a shared oracle. `wire/src/lib.rs`'s own doc rejects "re-declare them" because drift becomes "a silent, per-field mismatch", yet that is what Go does by necessity. Drift is caught only by the end-to-end conformance kit or by per-test comments ("named after them so a drift between the two walks shows"). The ids test's expected values were computed once by running the old TS plugin's JS through `node -e`. Only generated-file detection uses a shared corpus (`plugins/sdk/testdata/generated_headers.json`, read by both Rust and Go tests). D-opus-1's `.claude` gap is what this arrangement lets through. The gitignore subset was hand-rolled to keep `go.mod` dependency-free, a premise no longer true.
- **Proposed change:** add shared golden corpora under `plugins/sdk/testdata/` (or a top-level `contract/testdata/`), generated by Rust tests and read by Go tests, as `generated_headers.json` already is: (a) `wire_v2.jsonl`: canonical serialized `WireNode`/`WireEdge`/`ControlEnvelope`/`FileChangeDiff`/handshake lines that Go must round-trip byte-for-byte; (b) `ids.json`: input tuples and expected node/edge ids; (c) `walk_cases.json`: small trees (files, `.gitignore` lines, symlinks, baseline names) with the expected walked set. Rust has a `--bless` test that rewrites them from the real implementation; Go only reads them.
- **Benefit:** a wire, id or walk change in Rust fails a Go unit test immediately, not later in conformance or in production; the Go plugin can be changed independently with a fast local oracle.
- **Effort:** M. **Risk:** walk fixtures with symlinks need per-OS handling (Windows); the gitignore subset the Go side deliberately does not support must be marked per case, not hidden.
- **Evidence (measured):** `plugins/go/wire.go:3-12` "this file is this plugin's independent copy ... kept honest against drift by core/src/cli/plugin_check ... not by shared source"; `plugins/go/ids_test.go:5-26` (expected ids from a `node -e` script); `plugins/go/walk_test.go:116-120`; `plugins/go/generated_test.go:13` `sharedCasesPath = "../sdk/testdata/generated_headers.json"`; `plugins/go/ignore.go:8-10` "`go.mod` for this plugin has zero requirements today" vs `plugins/go/go.mod` `require golang.org/x/tools v0.50.0`.

## D-opus-7: `plugin.toml` has three independent Rust parsers (plus a Go reader) and no typed schema shared by core and the SDK

- **Location:** `core/src/daemon/manifest.rs:RawManifest` (856) and siblings `RawPlugin/RawSpawn/RawLanguages/RawFingerprint/RawWorkspace`; `plugins/sdk/src/manifest.rs:RawManifest` (182) with `RawPlugin/RawLanguages/RawWorkspace`; `plugins/sdk/src/lsp/config.rs:RawManifest` (461) with `RawPlugin/RawSemantic`; `plugins/go/manifest_test.go`.
- **Problem:** duplication of a boundary schema; leaky contract. `plugin.toml` is as much a core<->plugin contract as the wire, but only the wire has a shared crate. Each reader declares its own partial serde view of the same `[plugin]` table, so renaming or adding a key is a coordinated edit across core and two SDK modules with no compiler help, and the plugins additionally keep code copies of manifest values (`PluginSpec`, TS `project::EXCLUDE_DIRS`, Go `manifestExcludeDirs`) pinned equal by tests.
- **Proposed change:** a `manifest` module in `g-mesh-wire` (or a small `g-mesh-manifest` crate, serde + toml only) owning the typed raw schema of `plugin.toml` (`[plugin]`, `spawn`, `languages`, `workspace`, `semantic`, `capabilities`) and a single `parse(&str)`. Core's `daemon::manifest` keeps its validation/discovery logic on top; the SDK's `manifest.rs` and `lsp/config.rs` read their sections from the shared type. The SDK's `PluginSpec` fallback stays (the binary must work without a manifest beside it).
- **Benefit:** a manifest key change is one schema edit checked by the compiler on both sides; a new SDK-read section does not need a third private parser.
- **Effort:** M. **Risk:** the parsers differ in strictness on purpose (SDK: "reported and ignored rather than fatal"; core: refuses); the shared type must parse leniently (all-optional fields) and leave strictness to each caller. Core's MCP-facing manifest fields (`NonSymbolShapes`, `SymbolQueryPrefixes`, `ReexportRules`) can stay core-only if they are parsed as an untyped tail.
- **Evidence (measured):** `grep -n "struct Raw"` on the three files (lines above); `plugins/sdk/src/manifest.rs:5-19` "Core does not send them ... the plugin either re-reads the file or carries its own copy" (and the doc still cites `ignorePolicy.ts`, the pre-Rust TS plugin); `plugins/sdk/src/lsp/config.rs` `from_manifest_at` parses `[plugin.semantic]` with its own `RawManifest`.

## D-opus-8: Core's test suite uses the real plugins as fixtures, so no plugin change can be tested without all of core

- **Location:** `scripts/test-plugin-spawns.txt`, `scripts/test-select.sh:classify` (plugin rows), `core/tests/it/*`, `plugins/sdk/src/testing.rs` (`PluginCheck` locates core's binary two directories above the test binary).
- **Problem:** testability; coupling at test time in both directions. 87 of the 103 core test modules in the spawn map start a real language plugin (typescript 66, rust 62, python 50, go 47). Consequently `test-select.sh` in its default (CI) mode adds every core section for any change under `plugins/{python,rust,typescript}/*` or `plugins/go/*`, and any change under `wire/*` or `plugins/sdk/*` is `full=1`. In the other direction, each plugin's conformance test needs core's binary (with ONNX Runtime and SQLite) built. The boundary is clean at link time (no plugin links core) but not at test time.
- **Proposed change:** split core's plugin-spawning tests by what they test. Tests of core behaviour (storage, watcher, linking, MCP shapes) move to the existing `g-mesh-fake-plugin`, driven by scripted `FileGraph` output so the fixture states exactly the nodes/edges the test needs. Tests whose subject is a language's output move into that plugin's crate (`plugins/<lang>/tests`, via `PluginCheck --expect` or the conformance fixtures). Keep a small, named set of end-to-end core+real-plugin tests (`core-spawns-<lang>`, already a section) as the integration layer. Then `test-select.sh` can map `plugins/<lang>/*` to `plugin-<lang>` + `core-spawns-<lang>` in CI too, as it already does in narrow mode.
- **Benefit:** a plugin-only change runs its plugin section plus a small e2e slice instead of every core section; a core change no longer fails because a language server or plugin output changed.
- **Effort:** L (many tests, done incrementally per module; the spawn map already lists them). **Risk:** losing real coverage of a core path that only a real plugin exercises; mitigated by keeping `core-spawns-*` and moving tests rather than deleting them. Fake-plugin fixtures can drift from real plugin output: pin a few fixtures by recording them from the real plugin.
- **Evidence (measured):** `awk` over `scripts/test-plugin-spawns.txt`: 103 rows, `none` 16, `typescript` 66, `rust` 62, `python` 50, `go` 47; `scripts/test-select.sh:160` `wire/* | plugins/sdk/*) full=1`; `:181-187` default-mode plugin row `add "plugin-$plugin" "${CORE[@]}"`; `plugins/sdk/src/testing.rs:36-55` (core binary searched "two directories up"). inferred: the CI cost and flakiness attribution benefits.

## D-opus-9: `plugin_version` lives in two to three places per plugin with two different bump rules

- **Location:** `plugins/{rust,python,typescript}/Cargo.toml` `[package] version` vs `plugins/*/plugin.toml` `plugin_version`; `plugins/go/wire.go:pluginVersion` vs `plugins/go/plugin.toml`; enforcement in `scripts/cut-release.sh:check_crate_backed_plugin_versions` and three `the_manifest_version_matches_the_crates` tests.
- **Problem:** config sprawl; one fact, several copies, held equal by a release script and tests. Cargo plugin crates are in the workspace version sweep (sdk/wire/walk are bumped every release) while `plugin_version` must move only when the plugin changed; the same `[package] version` serves both rules. In this review worktree the release bump moved the plugin crates to 4.30.0 while every `plugin.toml` stayed 4.28.0, the exact disagreement the tests and `cut-release.sh` refuse.
- **Proposed change:** make `plugin.toml`'s `plugin_version` the single source for crate-backed plugins and derive it rather than copy it: either the bundle step (which already regenerates the installed manifest, D-opus-2) writes `plugin_version` from `CARGO_PKG_VERSION`, with the checked-in `plugin.toml` omitting it, or the plugin binary reports `env!("CARGO_PKG_VERSION")` in its handshake and core reads the version from there. For Go, generate `pluginVersion` from `plugin.toml` with `go:embed` instead of a const.
- **Benefit:** a plugin release is one version edit; a workspace-wide bump can no longer desynchronise a plugin.
- **Effort:** S-M. **Risk:** `g-mesh plugins list` reads the version before spawning, so the handshake option changes when the number is known; the bundle-time option keeps that.
- **Evidence (measured):** worktree: `plugins/rust/Cargo.toml:3 version = "4.30.0"`, `plugins/rust/plugin.toml:32 plugin_version = "4.28.0"` (same for python, typescript); main checkout `HEAD`: both `4.28.0`; `scripts/cut-release.sh:46-69` describes the two rules; `cut-release.sh:466-` `check_crate_backed_plugin_versions` refuses disagreement.

## D-opus-10: `lsp/bridge.rs` mixes four concerns in one 3.4k-line production file

- **Location:** `plugins/sdk/src/lsp/bridge.rs`: `Budgets`/`LspBridge` lifecycle (132-960), question generation `Question/Ask/Questions/questions` (965-1257), answer mapping `Answers`, landing/overload/hover (`Overloaded`, `choose_overload`, `hover_text`, `normalise_hover`, `hover_matches`, `without_first_parameter`) (1258-2415), the pass loop `run_pass/record_answer/trim_untyped_calls/record_implementor` (2416-3138), `impl SemanticEngine` (3139-3393), tests (3394-5195).
- **Problem:** god module (cohesion). The engine is generic and has a configuration seam already (`SemanticConfig`, `OverloadDisambiguation`), but the code that decides how a server's answer becomes an edge, which is where per-server quirks land, sits in the same file as process lifecycle, budgets and readiness. Each new server quirk (rust-analyzer, pyright, vtsls are all discussed in its docs) is a diff into the file that also owns timeouts and restarts.
- **Proposed change:** split into `lsp/questions.rs` (what to ask for an index), `lsp/answers.rs` (locations -> landing -> overload choice -> recorded edge, hover normalisation), `lsp/pass.rs` (`run_pass`, timing, retract), leaving `bridge.rs` with `LspBridge`, `Budgets` and the `SemanticEngine` impl. Items stay `pub(super)`; tests move with the code they test.
- **Benefit:** answer-mapping changes for one server become reviewable and testable without touching lifecycle/budget code; the pure answer functions become unit-testable without a fake LSP process.
- **Effort:** M (mechanical, but large). **Risk:** low functional risk; merge conflicts with in-flight semantic-tier work.
- **Evidence (measured):** `grep -n "^struct\|^fn\|^impl\|^enum"` on `bridge.rs` (line ranges above); module map 6.2 `src/lsp/bridge.rs` 5195 lines, 1801 inline test; `lsp/config.rs:202-215` `OverloadDisambiguation { None, Hover }`; `find_implementations(Extractor)` and the SDK outline show the bridge is the only `SemanticEngine` behind all three cargo plugins (`plugins/*/src/semantic.rs` all hand a `SemanticConfig` to `LspBridge`). inferred: benefit.

## Considered and rejected

- Per-plugin `project/facts.rs` with `Facts::of/encode/decode` + `resolution_delta` in three plugins: the shape is already a trait seam (`Extractor::resolution_facts/resolution_delta`, `plugins/sdk/src/lib.rs`); the bodies are language-specific (471 changed lines between Rust and Python).
- Rust/Python `extractor/{scope,model,keys,syntax}.rs` parallel structure: same decomposition, different content (743/619 changed lines in diffs); sharing would be an abstraction without shared code.
- Moving the conformance kit (`core/src/cli/plugin_check`, 6.3k lines) into its own crate so plugins need not build core: it deliberately indexes through core's real storage, graph and MCP layers (imports `storage::index_store`, `mcp::query_shapes`, `watcher::apply`); extraction would duplicate or fake core. D-opus-8 handles the test-time coupling instead.
- Moving the Rust plugin's OS sandbox (`sandbox.rs` + `landlock_ns.rs`, ~2.8k lines) to the SDK: only rust-analyzer executes project code (build scripts, proc-macros); pyright and vtsls do not, so it is correctly language-owned.
- `g-mesh-wire` and `g-mesh-walk` as separate crates: correctly minimal (serde only; ignore only), no inbound edge from plugins to core; the `json-schema` feature keeps schemars out of plugins.
- Go plugin re-implementing framing/control loop instead of the SDK: unavoidable across languages; the risk is addressed by D-opus-6, not by merging.
- `hold.rs` / `hold.go` test knobs compiled into production plugins: tiny, env-gated, and needed to test across a process boundary.
- `ci.yml` size (1.3k lines): mostly per-OS provisioning and diagnostics; the part worth fixing (section list drift) is in D-opus-5.
