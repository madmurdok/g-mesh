## B-fable-1. Placeholder `nativeKind` vocabulary is a wire contract defined in three graph pass modules

- **Location:** `core/src/graph/symbol_links.rs:305,311,317` (`PENDING_SYMBOL_NATIVE_KIND`, `REEXPORT_NATIVE_KIND`, `REEXPORT_ALL_NAME`), `core/src/graph/containers.rs:197` (`CONTAINER_NATIVE_KIND`), `core/src/graph/imports.rs:97,116` (`RESOLVED_MODULE_NATIVE_KIND`, `EXTERNAL_MODULE_NATIVE_KIND`).
- **Problem (dependency direction, duplication):** these strings are what a plugin writes on the wire, but core's copy lives beside the linking algorithms. Anything that only needs the vocabulary imports a linking pass: `protocol/conformance.rs:7-9` imports all three pass modules (the whole `protocol -> graph` edge, 3 sites, and so the `graph <-> protocol` cycle); `storage/language_swap.rs:57-58` imports two of them; `graph/queries.rs:4-6` imports all three, while `containers.rs:192` and `symbol_links.rs:297` import `queries` back (a cycle inside `graph`). The same strings are spelled again in `plugins/sdk/src/graph.rs:238-241`, `plugins/sdk/src/lsp/bridge.rs:2028` and `plugins/go/extract.go:107-117`.
- **Proposed change:** put the constants (and `REEXPORT_ALL_NAME`) in `g-mesh-wire` as one `native_kind` module; the SDK's `PlaceholderKind` mapping and core both read them from there. In core, `graph::queries::NON_DECLARATION_NATIVE_KINDS` is built from the wire constants; the pass modules stop exporting them. Callers change their `use` line only (files measured: `graph/{queries,containers,imports,symbol_links}.rs`, `protocol/conformance.rs`, `storage/{language_swap,index_store}.rs`, `mcp/unlinked.rs`, `cli/deps.rs`, `cli/plugin_check/checks.rs`). The Go plugin keeps its own copy (separate module) but gains one named source to compare against.
- **Benefit:** adding or renaming a placeholder kind is one edit in the crate that already owns the contract; `protocol` no longer depends on `graph`; a linking pass can be rewritten without touching conformance or storage.
- **Effort:** S. **Risk:** low; pure move of `&str` constants. `schema.rs:272` hard-codes `'pending_symbol'` in a partial index on purpose (comment at :271) and stays as is.
- **Evidence:** all line references above measured by `grep -rnE "pub const (…_NATIVE_KIND|REEXPORT_ALL_NAME)"` and a per-constant `grep -rl` over `core/src` excluding test files. That the wire crate is the right home is inferred from its module doc in the map ("every type that crosses the boundary between core and a language plugin").

## B-fable-2. `project_walk` takes its baseline excludes from `watcher`, and the SDK keeps a second copy

- **Location:** `core/src/project_walk.rs:31,170`; `core/src/watcher/mod.rs:34`; `plugins/sdk/src/walk.rs:50`.
- **Problem (dependency direction, duplication):** `project_walk` (data) imports `watcher::BASELINE_EXCLUDED_DIRS` (runtime) while `watcher` imports `project_walk` (3 sites): the `project_walk <-> watcher` cycle in the map is this one constant. The identical `[".git", ".claude"]` array is declared again in the SDK, kept in step by a comment (`watcher/mod.rs:30`: "The same pair as `BASELINE_EXCLUDED_DIRS` in plugins/sdk/src/walk.rs").

- **Benefit:** a change to the baseline (a third directory) cannot make the watcher, core's walk and the plugins' walk disagree about which files exist; `project_walk` becomes a leaf over `g-mesh-walk`.
- **Effort:** S. **Risk:** low. `g-mesh-walk` gains a policy constant; today it takes the names as a parameter, so its API does not change.
- **Evidence:** measured by `grep -rn BASELINE_EXCLUDED_DIRS` over `core/src`, `walk/src`, `plugins/sdk/src` (no hit in `walk/src`). Module-map section 5 lists the cycle as 1/0 vs 3/0.

## B-fable-3. `storage::connection` derives the index location from `daemon::identity`

- **Location:** `core/src/storage/connection.rs:7,35,70` (`project_hash`, `identity::record_project_root`); `core/src/daemon/identity.rs`.
- **Problem (dependency direction, cohesion):** where a project's state directory is (`projects_root`, `project_dir`, `ensure_project_dir`) is split over three modules: `paths` (home), `storage::connection` (join + create) and `daemon::identity` (hash + root record). The single non-test `storage -> daemon` `use` is this import, so it alone closes the `daemon <-> storage` cycle (29/1 the other way). `config/mod.rs:54,251` reaches into `storage::connection` for `project_dir`/`ensure_project_dir`, which is why `config -> storage` exists and why `embedding -> config` puts embedding in a loop with storage through config.
- **Proposed change:** move `identity.rs` (it imports only `std`, `anyhow`, `sha2`: measured, lines 1-5) and the three directory functions into `paths` (or `paths::project`). `storage::connection` keeps only opening connections. `config`, `cli/clean.rs` and `daemon` import from `paths`.
- **Benefit:** changing the on-disk layout or the project-identity rule touches one leaf module; `storage` no longer needs `daemon` to compile, `config` no longer needs `storage`.
- **Effort:** S. **Risk:** low; re-export from the old paths during the move. Integration tests name `project_hash` (4 files under `core/tests/it`).
- **Evidence:** `find_references(project_hash, answer: files)`: 15 references in `cli/clean.rs` (3), `daemon/identity.rs` (2), `storage/connection.rs` (2) and four `core/tests/it` files (2 each). `grep -n "crate::storage\|crate::paths" config/mod.rs`. That no other non-test `storage -> daemon` site exists is measured by my grep of `crate::daemon` under `storage/` (the remaining hits, `index_store.rs:820,830`, are after line 609 `mod tests`).

## B-fable-4. The embedding backfill takes the daemon's `IndexingStatus` to report two counters

- **Location:** `core/src/embedding/backfill.rs:102,179,199,249`.
- **Problem (dependency direction, missing seam):** `backfill::run(store, embedding, progress: &IndexingStatus)` uses exactly two methods, `set_embed_total` and `add_embed_done`. For that it imports a 1020-line daemon type, which is the whole `embedding -> daemon` edge and the `daemon <-> embedding` cycle.
- **Proposed change:** `embedding` declares `trait EmbedProgress { fn set_total(&self, u64); fn add_done(&self, u64); }` (or `run` takes `&dyn Fn(Progress)`); `IndexingStatus` implements it in `daemon`. Callers of `run` pass the same value.
- **Benefit:** the backfill can be driven from the CLI or a test with a counter stub; changes to the indexing-phase model stay in `daemon`.
- **Effort:** S. **Risk:** low.
- **Evidence:** `find_references(IndexingStatus, file_paths: [embedding/backfill.rs, embedding/pipeline.rs, storage/index_store.rs], answer: files)`: 2 references, both in `backfill.rs`. `grep -n "progress\." embedding/backfill.rs` gives lines 199 and 249 only (non-test part).

## B-fable-5. Record types live in the write path and the linking passes live in the query module: `graph <-> storage`

- **Location:** `core/src/storage/write.rs` (`NodeRecord`, `EdgeRecord`, `Diff`, `PlaceholderTargetRecord`, `apply_diff`/`write_diff`); `core/src/storage/index_store.rs:41-42,129-133,164-175,344-352`; `core/src/storage/write.rs:6,398,652`; `core/src/graph/{containers,imports,symbol_links}.rs`.
- **Problem (cohesion, dependency direction):** two things are fused.
  1. The row model that every layer speaks is declared in the module that executes writes. `NodeRecord` has 167 references in 34 files, including read-only MCP handlers, so `mcp/find_definition.rs` depends on `storage::write` to name a row.
  2. `graph` holds both read-side code (`queries`, `pagination`, `traversal`, `resume_token`) and write-side passes that mutate the index (`containers::detach/attach`, `imports::link_*`, `symbol_links::link_*`). Storage calls up into those passes (`write.rs:398,652` and `index_store.rs` `link_applied`/`link_all`), while the passes and the readers call down into `storage::write` for the types. Result: 7/1 vs 5/0 sites, a real two-way dependency, and neither module can be built or tested alone.
- **Proposed change:** (a) a leaf `core/src/model.rs` (or `storage::records`) with the record types and `Diff`, no SQL; `storage::write` keeps only `apply_diff` and friends. (b) Split `graph` by role: `graph::link::{containers,imports,symbol_links}` (write side, called by the store) and `graph::read::{queries,pagination,traversal,resume_token}`. Then `storage::{write,index_store} -> graph::link -> model` and `mcp -> graph::read -> model` are both one-way. If the split of `graph` is too large for one step, (a) alone already removes every `graph -> storage::write` type import (measured: `containers.rs:193`, `imports.rs:92`, `symbol_links.rs:300`, `traversal.rs:9`, `queries.rs:7`, `pagination.rs:6`), leaving `symbol_links -> storage::qualified_path` and `queries.rs:166` as the only upward sites.
- **Benefit:** a change to how rows are written (batching, transaction shape) no longer recompiles or risks the readers; a new linking pass has an obvious home and an obvious caller; MCP handlers stop depending on the write module.
- **Effort:** M ((a) is mechanical but touches 34 files' imports; (b) is module moves). **Risk:** import churn across `mcp`, `daemon`, `watcher`, tests; `containers::detach/attach` are `pub(crate)` and sit inside `write_diff`'s transaction, so the call order must be preserved exactly.
- **Evidence:** `find_references(NodeRecord, answer: files)`: total 167, 34 files. Lines above from my edge grep of `crate::graph`/`crate::storage` under both directories. `index_store.rs:164-175` read directly (`imports::link_diff` then `symbol_links::link_diff` inside the store's hold).

## B-fable-6. The index store and the language swap know the embedding pipeline

- **Location:** `core/src/storage/index_store.rs:39-40,363-368,549-551`; `core/src/storage/language_swap.rs:54-56,418,496,511,624-626`; `core/src/embedding/{pipeline,backfill,cache}.rs` importing `storage`.
- **Problem (dependency direction, leaky abstraction):** `IndexStore::swap_language` and `Writer::store_vectors` take `&EmbeddingPipeline` and `&ComputedBatch` and do nothing with them but call `embedding.store(conn, computed)` (`index_store.rs:550`, `language_swap.rs:625`). `language_swap::plan_embeddings` builds an `EmbedInput` and calls `node_text` to decide whether a node's embedded text changed. Meanwhile `embedding` needs `storage::{vectors, schema, write, index_store}`. So the store cannot be tested without the embedding types (and its ONNX/tokenizer dependencies) in the build, and a change to the pipeline's batch type is a change to storage's public API.
- **Proposed change:** storage declares the seam and embedding implements it: `trait VectorWrite { fn store(&self, conn: &Connection); }` (or `Option<&dyn Fn(&Connection)>`) for the two store-and-forward sites, and `plan` takes `text_of: &dyn Fn(&NodeTextRow) -> Option<String>` (or a `NodeText` trait) for the changed-text comparison. `daemon::workspace_reindex` and `watcher::apply`, which already hold both the store and the pipeline, pass the pipeline in through the trait.
- **Benefit:** `storage` becomes independent of `embedding` (one-way `embedding -> storage`); swapping the embedding model, batch shape or text form does not touch the store or the swap; swap tests need no pipeline fake.
- **Effort:** M. **Risk:** `swap_attached` (185 lines) and `plan_attached` (197 lines) are the area's largest functions after `write_diff`; the vectors must still be written inside the swap's single transaction (`index_store.rs:361-362` states that invariant), which a callback preserves.
- **Evidence:** lines above measured by `grep -nE "EmbeddingPipeline|ComputedBatch|node_text|EmbedInput"` on `language_swap.rs` and by reading `index_store.rs:344-398,545-563`. Module-map: `embedding <-> storage` 6/1 vs 5/0.

## B-fable-7. `storage::schema` is DDL plus the daemon's whole per-language state machine

- **Location:** `core/src/storage/schema.rs` (2250 lines non-test, 64 `pub` items, 94 SQL call sites before its test module).
- **Problem (god module, cohesion):** one file owns (a) the DDL for 25 tables and the generation check (`apply`, `ensure_current`, `reset`, lines 101-870), and (b) about 60 free functions that are the persistence of runtime workflows: bulk-index outcomes, retries, pending reindexes, owed re-extracts, semantic pass / residual / pending / owed files, resolution facts and watch paths, seed origin, noise purge (lines 878-2227). Group (b) is called from `daemon`, `watcher`, `mcp`, `cli` and `embedding`, each using a different subset; its domain type `LanguageOutcome` is imported from `languages` (`schema.rs:6`), which is the `storage -> languages` edge. Any change to, say, semantic-pass bookkeeping edits the same file as the node/edge schema.
- **Proposed change:** keep `schema.rs` as DDL + generation only. Move the accessor groups into sibling modules by table family, each with its DDL fragment exported as a `const` that `schema::apply` concatenates: `storage::state::{bulk, retry, reindex_owed, semantic, resolution, seed, embedding_meta}`. No behaviour change; callers change `schema::x` to `state::semantic::x`. `LanguageOutcome` moves with `state::bulk` or stays in `languages` (see 11).
- **Benefit:** a new piece of daemon bookkeeping is a new small module rather than another 80 lines in the schema file; the semantic-pass state (the largest family, roughly lines 1422-2120) can be reviewed and tested apart from the DDL; fewer merge conflicts on one hot file.
- **Effort:** M (mechanical, but about 60 functions and their tests in `schema/tests.rs`, 1664 lines). **Risk:** low for behaviour; `CURRENT_SCHEMA_VERSION` semantics must not change, and tables "added by `CREATE TABLE IF NOT EXISTS`" (comments at 532, 610, 626, 640, 663, 703, 726, 741) must keep being applied on every open.
- **Evidence:** `grep -nE "^\s*pub(\([a-z]+\))? (fn|struct|enum|trait|type|const) " storage/schema.rs` (list read in full), `grep -c "CREATE TABLE IF NOT EXISTS [a-z_]* ("` (25 statements), and a per-function `grep -rl` for 12 sampled accessors showing callers in `daemon`, `watcher`, `mcp`, `cli`, `embedding`, `storage`. The grouping into families is inferred from names and line order, not from reading every body.

## B-fable-8. Table and column names are written out in SQL across runtime and surface modules

- **Location (non-test SQL call sites outside `storage/` and `graph/`):** `cli/status.rs` (6), `watcher/apply.rs` (5), `daemon/config_reindex.rs` (5), `mcp/overrides.rs` (4), `gc/last_used.rs` (3), `cli/plugin_check/session.rs` (3), `mcp/unlinked.rs` (2), `daemon/registry.rs` (2), `daemon/bulk_index.rs` (2), `cli/deps.rs` (2), `watcher/staleness.rs` (1), `mcp/untyped.rs` (1), `daemon/semantic.rs` (1); plus `embedding/backfill.rs` (3) and `cli/embed_eval.rs` (7).
- **Problem (leaky abstraction, duplication):** `IndexStore` hands out the raw `rusqlite::Connection` (`with`, `lock`, `read`, `Writer::step`), and callers use it to write their own SQL against `nodes`, `edges`, `indexed_files`, `meta`, `vectors`, `containers`, `placeholder_targets`. The same question is asked several ways: "the indexed files (of a language)" is `SELECT … FROM nodes WHERE kind = 'File' …` at `cli/status.rs:874`, `daemon/registry.rs:352,399`, `daemon/config_reindex.rs:302,311`, `daemon/semantic.rs:195`, `daemon/bulk_index.rs:312`. `cli/status.rs:487,519` and `gc/last_used.rs:129` probe `sqlite_master` for tables by name. A column rename or a table split is therefore a change in at least 13 files outside the area, none of which the schema module can point at.
- **Proposed change:** give these questions names in area B and move the SQL there: `graph::read::files` (`indexed_file_paths(conn, language: Option<&str>)`, `file_count_by_language`, `files_with_syntax_errors`), `storage::state` accessors for `indexed_files` baselines and `meta.lastUsed`, and move the edge/node probes of `mcp/{overrides,unlinked,untyped}.rs` into `graph::read` next to `queries`. Leave `Connection` access on `IndexStore` (see "Considered and rejected"), but add a test that greps for SQL verbs outside `storage/` and `graph/` with an allow-list, so the count goes down, not up.
- **Benefit:** schema changes become local to B; the file-listing rule (for example, whether `filePath <> ''` excludes containers) is decided once.
- **Effort:** M (about 38 sites; each is a small move). **Risk:** low per site; a few queries are tuned to their caller (`config_reindex.rs:387` is a five-table join) and should move verbatim.
- **Evidence:** measured by `awk` over every non-test `.rs` file under `core/src`, counting `.prepare(`, `.prepare_cached(`, `.query_row(`, `.execute(`, `.execute_batch(` on non-comment lines before the first top-level `#[cfg(test)]`. The count can miss a statement whose call and SQL are split unusually, or SQL passed through a helper, so read it as a lower bound. `find_callers(IndexStore::with, answer: files)`: 123 callers; `find_callers(IndexStore::lock, answer: files)`: 75; `find_callers(Writer::step, answer: files)`: 20 (each total includes test files; `with` and `lock` each report one untyped-receiver call, in `cli/embed_eval.rs` and `process.rs`).

## B-fable-9. `graph::pagination` carries the MCP response byte budget

- **Location:** `core/src/graph/pagination.rs:10-55,103-206,423-440,963` (`DEFAULT_PAGE_SIZE`, `MAX_PAGE_SIZE`, `resolve_page_size`, `MAX_RESPONSE_BYTES`, `OUTLINE_MAX_RESPONSE_BYTES`, `longest_prefix_fitting`, `bound_page`, `wire_len`, `fit_budget*`, `bound_page_in_response`, `truncate_to_bytes`, `FILE_TALLY_MAX_BYTES`, `EXCLUDED_TALLY_MAX_BYTES`, `bound_defines_page`) versus `:304-1043` (`EdgeRank`, `Direction`, `paginate_edges`, `count_edges*`, `tally_edge_files*`, `paginate_defines`, `paginate_by_score`).
- **Problem (cohesion):** one 2125-line file with 36 `pub` items holds two unrelated things: SQL keyset pagination over edges, and how many serialized JSON bytes an MCP tool response may carry. - **Effort:** S-M. **Risk:** `cli` uses `graph` at 4 sites; I did not check whether any of them uses the byte-budget functions (if so they import from `mcp`, which `cli` already does).
- **Evidence:** `pub` item list measured by grep on `pagination.rs`. `find_references(MAX_RESPONSE_BYTES, answer: files)`: 9 references, all in `graph/pagination.rs` (2) and `mcp/*` (7). That the other budget functions are also MCP-only is inferred from this one constant and their names; not checked per function.

## B-fable-10. `embedding` reads the global config and environment from inside its constructors

- **Location:** `core/src/embedding/pipeline.rs:115-125` (`CacheSettings::from_global_config`), `core/src/embedding/rerank.rs:318-326` (`RerankSettings::from_environment`), `core/src/embedding/model.rs:127` (`embedding_version` compares against `EmbeddingConfig::default().model`), `core/src/embedding/cache.rs:112` (`paths::g_mesh_home()`).
- **Problem (config sprawl, testability, error-handling consistency):** `EmbeddingPipeline::load(config: &EmbeddingConfig)` receives one section of the config from its caller, then re-reads the global config file itself for two more sections (`embedding_cache`, `rerank`), each with its own log-and-default on a read error and its own env override. The caller cannot see or control those inputs; tests go through separate `pub(crate)` constructors (`load_at`, `with_loader`, `with_reranker`) to avoid them. This is also the `embedding -> config` edge (1/3) that ties area B to area C.
- **Proposed change:** one `EmbeddingSettings { model: EmbeddingConfig, cache: Option<CacheSettings>, rerank: RerankSettings }` built once by the caller (daemon start, CLI) from config + env, with one error path; `EmbeddingPipeline::load(&EmbeddingSettings)`. `embedding_version` takes the default model name as data. The settings struct can live in `embedding`, with `config` holding only the serde sections.
- **Benefit:** a new embedding knob is added in one place; config read errors are reported once and the same way; embedding can be constructed in tests with plain values and stops depending on `config`.
- **Effort:** S. **Risk:** the env overrides (`cache::CACHE_ENV`, `RERANK_ENV`) must keep precedence over the file.
- **Evidence:** the three excerpts read directly. `find_callers(RerankSettings::from_environment)`: one caller, `RerankModelState::from_environment` (`rerank.rs:351`), plus one non-call reference. I did not trace who calls `CacheSettings::from_global_config`; that it runs under `EmbeddingPipeline::load` is inferred from `load_with_cache(config, cache: Option<CacheSettings>)` beside it.

## B-fable-11. `languages` (what core knows without a plugin) depends on the daemon's manifest module

- **Location:** `core/src/languages.rs:42,157-260`; `core/src/daemon/manifest.rs` (`extension_of`, `under_excluded_dir:652`, `DiscoveredPlugins`).
- **Problem (dependency direction):** the catalogue's module doc says it is what core knows about a language without its plugin, yet three of its public functions take `&DiscoveredPlugins` and it borrows two path helpers from `daemon::manifest`. That is the `languages -> daemon` edge and the `daemon <-> languages` cycle. `DiscoveredPlugins` is used for two facts only: is language X installed (`manifests.contains_key`, lines 205, 217) and which language owns this path (`language_for`, line 213), plus the installed plugins' `exclude_dirs`.

- **Evidence:** `grep -n "discovered\.\|DiscoveredPlugins" languages.rs` (lines listed above). `find_callers(under_excluded_dir, answer: files)`: 6 callers in `daemon/registry.rs` (2), `languages.rs` (2), `cli/plugin_check/checks.rs` (1), `daemon/manifest.rs` (1).

## B-fable-12. The "node row -> embedded text" mapping is rebuilt in four non-test places

- **Location:** `core/src/embedding/pipeline.rs:861` (`From<&NodeRecord> for EmbedInput`), `core/src/embedding/pipeline.rs:879-890` (`current_embeddable_text`, own `SELECT kind, name, qualifiedName, filePath, docComment, signature, generated`), `core/src/embedding/backfill.rs:320-333,386,423` (two more SELECTs and constructions), `core/src/storage/language_swap.rs:410-428` (row struct + `EmbedInput { … }`); also `cli/embed_eval.rs:296` and `cli/embed_eval/schedule.rs:292`.
- **Problem (duplication):** which `nodes` columns feed the embedded text is stated once in `EmbedInput` but the column list and the row-to-input mapping are repeated per caller. - **Benefit:** changing the text form is one edit plus the version tag.
- **Effort:** S. **Risk:** low; `backfill.rs:423` also selects `visibility` for its tiering and keeps that extra column.
- **Evidence:** `grep -rn "EmbedInput {"` over `core/src`; non-test status of the `pipeline.rs` sites checked against the file outline (test module starts at line 930). The stale-vector consequence is inferred.

## Considered and rejected

- **`IndexStore` exposing `Connection` (`with`/`lock`/`read`/`step`) is not itself the problem.** Its doc and ADR 0001 make it the owner of the lock and hold duration, and `graph` is designed as functions over `&Connection`. The leak is SQL text outside B (finding 8), not the handle.
- **`paths.rs` (96 lines, fan-out 0, fan-in 6)** is a correct leaf; nothing to change beyond receiving finding 3's functions.
- **`embedding/model.rs` (1907 lines) and `rerank.rs`** hold ONNX loading and scoring behind `Embedder`/`Scorer` traits already; large but cohesive. Not split.
- **`symbol_links.rs` (2174 lines)** is one algorithm with one entry pair (`link_all`/`link_diff`) and 11 `pub` items; size alone is not a coupling problem.
- **`storage -> protocol` (`QualifiedPath` in `qualified_path.rs`, `write.rs`)** is a dependency on a wire type re-exported by `protocol::types`; importing it from `g_mesh_wire` directly would drop the edge, but it is a one-line cosmetic change, not a seam.
- **`graph::resume_token` gzip+base64 format in `graph`** looked like surface encoding, but the token carries traversal state (`VisitedNode`) and is consumed by `traversal`; it belongs there.
- **`cli -> embedding` 18/2** is mostly `cli/embed_eval` (an eval instrument, 8270 lines); it is an area C question whether that tool belongs in the binary, not a defect of the embedding API.
- **`embedding::cache` owning its own SQLite file with 22 SQL sites** is a separate machine-wide database, not the index; correctly outside `storage::schema`.
- **Extracting area B into its own crate now** is not proposed: until findings 1-6 and 11 land, B is inside the 13-module SCC and a crate boundary cannot be drawn.
