01 Зачем это нужно

Когда ИИ-агент работает с кодом, ему регулярно нужно отвечать на вопросы вроде «кто вызывает эту функцию» или «что реализует этот интерфейс». Без специального инструмента агент решает это грепом и чтением файлов — работает, но медленно и ненадёжно: текстовый поиск не отличает вызов функции от комментария с тем же именем, не проходит через реэкспорты и алиасы импортов, не умеет сказать «а вот тут я не уверен».

g-mesh — локальный индексатор кода. Он один раз проходит по проекту, строит граф: файлы, функции, типы, переменные — и связи между ними (кто кого вызывает, что от чего наследует, кто что импортирует). Дальше граф отдаётся агенту через протокол MCP — набором точных инструментов вида «найди определение», «найди всех вызывающих», «покажи зависимости файла». Поверх графа планируется слой семантического поиска по смыслу (эмбеддинги) — для случаев, когда агент не знает точное имя символа.

Ключевая идея: граф — это источник истины, эмбеддинги — это надстройка для поиска. Так система остаётся точной там, где точность возможна (структура кода — это факт, а не догадка), и подключает более мягкий, вероятностный поиск только там, где без него не обойтись.

02 Из чего состоит система

Система — это четыре независимых процесса, которые запускаются и живут по-разному. Ниже — карта того, кто с кем разговаривает и по какому каналу.

Шим (mcp-shim)

Без памяти между вызовами. MCP-клиент запускает его как обычный stdio-сервер — так же, как любой другой MCP-инструмент. Шим считает хэш пути проекта, ищет живой сокет демона, при необходимости поднимает демон в фоне и дальше просто перекладывает байты между stdin/stdout и Unix-сокетом, не заглядывая внутрь сообщений.

Демон-ядро

Один процесс на проект (хотя бы теоретически — про фактические таймауты см. раздел «Что задумано»). Держит открытым SQLite, слушает файловую систему, отвечает на MCP-запросы, управляет жизненным циклом процесса языкового плагина.

Языковой плагин

Отдельный процесс на язык. Для JS/TS — это tree-sitter (быстрый синтаксический разбор) плюс в перспективе TypeScript compiler API для более точного семантического разрешения. Только читает исходники проекта, в базу данных не пишет напрямую — только отправляет ядру список изменений.

SQLite-файл

Один файл на проект, в режиме WAL (Write-Ahead Log — запись сначала в отдельный лог, потом слияние с основным файлом; так чтение не блокирует запись). Хранит и граф (таблицы узлов/рёбер), и в будущем — векторы для семантического поиска.

03 Как поднимается процесс

Важная деталь дизайна: пользователю не нужно ничего «запускать» руками. Идентичность проекта — это просто хэш от канонического пути каталога. Переключил агента на другой проект — шим сам поймёт, к какому демону подключаться (или что нужно поднять новый).

Последовательность при первом обращении к новому проекту:

  1. Шим пытается подключиться к Unix-сокету по пути, зависящему от хэша проекта.
  2. Сокета нет — шим берёт файловую блокировку (bootstrap.lock) и ждёт её получения, а не гонится наперегонки с другими шимами: если два агента открылись в одном проекте одновременно, второй просто подождёт первого, а не запустит второй демон.
  3. Под блокировкой шим ещё раз проверяет сокет (вдруг кто-то уже поднял демон, пока мы ждали) и, если так и не появился — запускает демон как полностью отсоединённый процесс (свой process group, нулевые дескрипторы ввода-вывода) и опрашивает сокет каждые 20 мс до 10 секунд.
  4. Демон, в свою очередь, берёт отдельную блокировку (daemon.lock, не ту же, что у шима — иначе был бы взаимный тупик), открывает SQLite, проверяет версию схемы, поднимает процесс плагина.
  5. Если проект ещё не индексировался (или схема пересобралась с нуля) — демон запускает разовый, отдельный процесс плагина в режиме полного обхода (--bulk-index) и не открывает сокет для запросов, пока обход не завершится целиком. Это осознанный выбор: агент никогда не получит ответ по наполовину построенному графу.
  6. Только после этого стартует наблюдатель за файлами, открывается сокет — и демон готов принимать MCP-запросы.

Зачем два разных lock-файла у шима и демона? Шим держит свою блокировку, пока ждёт, что запущенный им демон станет доступен. Если бы демон пытался взять ту же блокировку — оба процесса заблокировали бы друг друга навсегда.

04 Хранилище: таблицы и файл на диске

Весь граф живёт в одном SQLite-файле — выбор в пользу простоты (один движок вместо графовой БД плюс отдельного векторного хранилища) ценой того, что рекурсивные запросы (обход графа) на SQLite медленнее, чем на специализированном графовом движке — это осознанный компромисс с чётко описанным порогом, после которого решение стоит пересмотреть (раздел 14).

Гранулярность — на уровне символа, а не строки: File, Module (пространство имён/пакет), Type (класс/интерфейс/структура), Function, Variable (только модульного уровня — локальные переменные внутри функций не индексируются, это был бы слишком большой объём данных без практической пользы для агента).

Схема специально языконезависима: вместо JS-шного «класс/интерфейс» и «extends/implements» — общий Type и одно ребро SUPERTYPE_OF для любого «наследует/реализует» отношения в любом языке. Особенности конкретного языка уходят в поле nativeKind, не размножая перечисление видов узлов.

Версия схемы — без миграций

Если версия схемы в файле не совпадает с ожидаемой (обновили ядро) — база просто стирается и строится заново. Никакого фреймворка миграций нет и не планируется: индекс — это воспроизводимый кэш, а не источник правды. Пересобрать дешевле, чем поддерживать миграции для данных, которые всегда можно восстановить из исходников.

Отдельная деталь: bulkIndexedAt в таблице meta — это не «версия схемы свежая», а именно факт «полный обход когда-то дошёл до конца». Если демон упал посреди обхода, при следующем запуске он честно увидит, что обход не завершён, и начнёт заново — а не решит, что раз схема на месте, то и данные полные.

05 Протокол ядро ↔ плагин

Ядро и языковой плагин общаются двумя разными каналами одновременно — сознательное разделение, потому что у этих каналов разная природа сообщений.

КаналФорматЗачем
Control-plane JSON-RPC 2.0 в LSP-стиле: заголовок Content-Length, затем тело Короткие команды запрос-ответ: «файл изменился», «статус», рукопожатие версии протокола. Такой же формат framing, что у tsserver — адаптер почти не нужен.
Bulk-поток NDJSON — один компактный JSON-объект на строку Первичный полный обход проекта: плагин может отдать сотни тысяч узлов и рёбер, не дожидаясь, пока всё поместится в памяти как один документ.

Оба канала защищены потолком размера в 64 мегабайта на одно сообщение (MAX_BODY_BYTES / MAX_LINE_BYTES) — так «сломанный» или недобросовестный плагин не сможет заставить ядро выделить неограниченную память под один пришедший кусок данных.

Рукопожатие и версия протокола

Перед началом работы плагин присылает своё имя, версию и версию протокола. Несовпадение версии протокола — это жёсткий отказ, а не попытка работать «как получится»: протокол — это код, а не данные, договориться о полусовместимости тут не с чем. (Для сравнения: несовпадение версии схемы БД — это просто сигнал переиндексировать всё с нуля, не ошибка.)

06 Первый запуск: холодная индексация

Когда демон впервые видит проект, он гонит один сплошной поток разбора — без ожидания «а что там с типами» — и делает граф доступным как можно раньше. 

sequenceDiagram
    participant Agent as Агент
    participant Shim as Шим
    participant Core as Ядро
    participant Plugin as Плагин
    participant DB as SQLite

    Agent->>Shim: запуск (stdio), рабочий каталог = проект
    Shim->>Shim: хэш(каталог), проверка сокета
    Shim->>Core: поднять демон
    Core->>Plugin: запустить языковой плагин (bulk-режим)
    Plugin->>Plugin: разбор tree-sitter (параллельно, по ядрам CPU)
    Plugin->>Plugin: резолвинг относительных путей импорта
    Plugin-->>Core: NDJSON-поток: узлы и рёбра
    Core->>DB: пакетные транзакции (~2000 элементов)
    Core->>DB: склейка резолвленных импортов с реальными файлами
    Core-->>Shim: индекс доступен

Внутри плагина tree-sitter — это синтаксический, а не семантический разбор: он строит дерево кода, не зная, что означает конкретное имя (нет проверки типов, нет понимания перегрузок). Именно поэтому «кто вызывает эту функцию» изначально решается неточно, а точные ответы там, где это возможно, получаются за счёт отдельного механизма — «склейки» графа, о которой ниже.

Разбор файла с синтаксической ошибкой (например, файл сохранён на середине правки) не проваливается целиком: tree-sitter — «терпимый к ошибкам» парсер, он выдаёт частичное дерево с узлом-«раной» на месте проблемного участка, а остальной файл разбирает как обычно. Стратегия обновления — «оставить последнее хорошее состояние», а не «стереть всё»: символы вне сломанного участка обновляются как обычно, а символы внутри или ниже него по файлу сохраняют предыдущее известное состояние, пока чистый разбор не подтвердит, что они правда удалены. Логика простая: ложное «символ, возможно, ещё существует» безопаснее для агента, чем ложное «символа точно больше нет» — второе может подтолкнуть к разрушительной правке на основе артефакта момента сохранения файла, а не реального состояния кода.

07 Как определяется, куда ведёт импорт

Это самая проработанная часть системы на сегодня (пять задач последнего релиза были посвящены именно ей). Задача: увидев в коде import x from "...", понять — какой реальный файл проекта имеется в виду, если вообще имеется. Строка-специфайер проверяется по цепочке из четырёх механизмов, по порядку, первый сработавший побеждает:

Почему именно такой порядок

Реальный пример из кода Excalidraw, на который ориентировался проект: пакет @excalidraw/element/* одновременно объявлен как воркспейс-пакет и замаплен через tsconfig paths на тот же каталог. Если бы оба механизма проверялись независимо и «побеждал последний ответивший», результат был бы недетерминированным. Вместо этого — жёсткий приоритет: путь от пакетного менеджера (воркспейс) побеждает всегда, а alias из tsconfig — это запасной вариант только тогда, когда воркспейс вообще ничего не нашёл. Резонно: воркспейс-манифест описывает, что реально загрузит Node/пакетный менеджер, а запись в paths — это подсказка для компилятора, которая может устареть и никак не проверяется при импорте.

«Существует» — это не просто stat()

На каждом шаге, прежде чем засчитать путь как найденный, система проверяет не только «файл физически есть на диске», но и «этот файл вообще попадёт в индекс при полном обходе». Иначе возникает конкретный баг, который был исправлен в последнем релизе: у собранного (не «сырого») монорепозитория объявленная точка входа пакета может указывать на dist/prod/index.js — файл, который физически существует, но который обход никогда бы не проиндексировал (он либо в .gitignore, либо в жёстко исключённом каталоге вроде dist//node_modules/). Раньше резолвер наивно говорил «да, файл есть» и указывал импорт именно туда — в файл без узла графа. Теперь резолвинг и обход файловой системы используют одну и ту же политику исключений, поэтому такой путь честно считается несуществующим, и перебор кандидатов проваливается дальше — к исходнику src/index.ts, который реально попадёт в граф.

Симлинки: теперь учитываются, с защитой от циклов

Ранее символические ссылки на каталоги были невидимы для обхода — из-за особенности API файловой системы Node.js ссылка не отвечает «я директория» и не отвечает «я файл», поэтому просто пропускалась. Это делало невидимыми целые пакеты в некоторых типичных для yarn/lerna раскладках монорепозиториев или в случаях, когда общий код подключён через симлинк. Решение — намеренно выбранная политика «следовать за ссылками», но только с защитой:

  • Идентичность — это реальный путь, полученный через разрешение ссылки (realpath), а не сама ссылка. Так система понимает, что два разных пути на самом деле указывают на одно и то же место.
  • Цикл (ссылка указывает на своего же «предка» по дереву) — отклоняется тем же способом, что и дубликат: реальный путь уже «занят».
  • Два пути на одно и то же (обычный каталог плюс ссылка-алиас на него) — индексируются один раз, под тем путём, который обход достиг первым по своему обычному отсортированному порядку обхода. Второй путь просто отбрасывается — не переименовывается, не сливается: идентичность узла здесь есть путь, которым до него дошли, и любое «канонизирование» сломало бы все специфайеры, которые на него ссылаются под старым именем.
  • Ссылка, ведущая за пределы корня проекта — отклоняется всегда; битая ссылка (указывает в никуда) — тихо пропускается, не роняя обход.

Забавная деталь, всплывшая при разработке: на macOS системный временный каталог /tmp сам является символической ссылкой на /private/tmp. Если не «канонизировать» корень проекта перед сравнением путей, вся защита от циклов и дублей тихо ломается именно на macOS — ссылка снаружи выглядит так, будто указывает «за пределы» корня, хотя на самом деле указывает внутрь него, просто записанного другим путём. Это было проверено вживую намеренной поломкой кода — без канонизации 3 из 4 вариантов записи одного и того же пути ломались.

08 Склейка графа: от заглушки к настоящему узлу

Плагин видит только один файл за раз. Когда он встречает import { foo } from "./x", он ещё не знает, существует ли файл ./x в индексе и правда ли там есть экспорт с именем foo. Поэтому вместо того, чтобы промолчать (и потерять связь навсегда) или гадать (и получить неверную связь), он честно создаёт узел-заглушку — временный Module-узел, на который вешается ребро — и отправляет это ядру. Ядро — единственная сторона, которая видит весь индекс сразу, и именно оно потом «дошивает» заглушку до настоящего узла. 

flowchart LR
    subgraph Плагин["Файл видит только себя"]
        A["import { foo } from './x'"] --> B["Module-заглушка
nativeKind: resolved_module

        B -->|IMPORTS| A
        A -->|CALLS на заглушку

    end
    subgraph Ядро["Видит весь индекс"]

    C -.-> F

Проход 1 — файлы (graph::imports)

Как только в графе появляется настоящий File-узел с нужным путём, все рёбра IMPORTS, ведущие на заглушку с этим же путём, перецепляются на него, а заглушка удаляется — если на неё больше ничего не ссылается (заглушка импорта может нести только одно такое ребро, так что удалять её после привязки безопасно).

Проход 2 — символы внутри файла (graph::symbol_links)

Тот же приём на уровень тоньше: заглушка адресуется как «путь-к-файлу#имя», и ядро ищет в этом файле ровно один подходящий по виду экспортированный символ (вызов — только на функцию, «наследует» — только на тип). Если подходит ровно один — ребро перецепляется и помечается разрешённым. Если ноль или больше одного — ребро остаётся как есть: правило простое и намеренное — лучше отсутствующая связь, чем неверная. На этом уровне не разрешаются: import * as ns (обращение к пространству имён — это уже семантика, кто есть ns.foo, structural-разбор не может достоверно сказать), default-импорт по умолчанию экспортированного именованного значения и реэкспорты вида export { x } from "./y" — эти случаи оставлены будущему семантическому слою (TypeScript compiler API).

Важная асимметрия: заглушка-файл удаляется после склейки, а заглушка-символ — нет, даже уже привязанная. Причина: на одну и ту же импортированную функцию в файле может быть несколько мест использования, и они добавляются со временем по мере правок; плагин при инкрементальном обновлении присылает только изменившиеся узлы, поэтому неизменная заглушка не будет переслана заново — удалить её значило бы оставить будущее новое ребро висящим в пустоте.

Когда это запускается

Оба прохода — и «весь индекс» (link_all), и «только этот диф» (link_diff) — идемпотентны, то есть безопасны для повторного запуска. Полный проход по всему индексу выполняется один раз, строго после того, как поток холодной индексации дошёл до конца (не раньше — иначе «ещё не дошли до этого файла» не отличить от «этого файла тут никогда не будет»). Диф-проход выполняется после каждого инкрементального изменения файла.

09 Инкрементальное обновление на лету

Индекс не пересобирается заново на каждое сохранение файла — наблюдатель за файловой системой (notify) ловит события изменения, плагин делает частичный tree-sitter-репарс (перестраивает только затронутое поддерево, а не весь файл целиком), и в базу летит только разница — добавленные/удалённые узлы и рёбра. 

sequenceDiagram
    participant FS as Файловая система
    participant W as Наблюдатель
    participant Core as Ядро
    participant Plugin as Плагин
    participant DB as SQLite

    FS-->>W: событие записи (файл сохранён)
    Core->>Plugin: файл изменился: X
    Plugin->>Plugin: инкрементальный tree-sitter-репарс
    Plugin-->>Core: диф (добавленные/удалённые узлы и рёбра)
    Core->>DB: одна транзакция
    Core->>Core: склейка импортов и символов, ограниченная этим дифом

Склейка на инкрементальном шаге умнее, чем «перепроверить только этот файл»: она также ловит заглушки в других файлах, которые ждали именно этого файла (если только что созданный файл — это цель чужого импорта), и новые использования символа, повешенные на уже существующую заглушку, которая сама не изменилась (и потому не попала в диф явно).

Расхождение с архитектурным планом. В плане описано «пачка изменений (например, git checkout) сливается в одну транзакцию» и «повторные сохранения одного файла гасятся» (debounce). Механизмы для этого — Debouncer и BurstBatcher — уже написаны и покрыты тестами, но ещё не подключены к реальному циклу демона: сегодня каждое отфильтрованное событие файловой системы вызывает обработку немедленно, одна транзакция на файл. Для обычной работы это не проблема (SQLite и так справляется), но при массовом переключении веток разница будет заметна как несколько сотен транзакций подряд вместо одной.

10 Обход графа и постраничные ответы

Большинство инструментов агента — однохопный вопрос («кто вызывает X», «что определено в этом файле») и отвечают обычной постраничной выборкой по курсору: «дай мне следующую страницу после этой отсортированной позиции». Один инструмент — get_dependencies — устроен сложнее: это транзитивный обход графа импортов на несколько шагов вглубь, и он реализован через рекурсивный SQL-запрос прямо внутри SQLite.

Три независимых предохранителя

Обход графа теоретически может «взорваться» — узел с тысячами исходящих связей (хаб) или очень глубокая цепочка. Против этого — три разных ограничения, каждое работает на своём уровне:

ОграничениеЧто делаетКак реализовано
maxDepth Не уходить глубже N шагов от стартового узла Простое условие WHERE глубина < maxDepth в рекурсивном запросе
maxFanout С одного узла брать не больше N исходящих связей за раз LIMIT прямо внутри подзапроса, который выбирает детей узла — так СУБД физически не читает больше нужного даже для узла с 20 000 связей
explorationBudget Общий бюджет «сколько строк движок вообще посмотрит» за весь запрос, независимо от того, что попадёт в итоговый ответ LIMIT на весь рекурсивный запрос целиком — «внутренний» предохранитель, отдельный от того, что видит вызывающая сторона

Ответ, который на что-то из этого наткнулся, никогда не отвечает молчаливым «всё, данных больше нет» — он честно помечен truncated: true и называет причину (truncatedBy). Продолжение разное для разной причины: срез по maxFanout — агент просто делает обычный постраничный запрос с того узла, где обрезало; срез по maxDepth — в ответе приходит список «узлов на границе», с которых можно перезапустить обход на следующую глубину; срез по бюджету — это отдельный механизм, описанный в следующем разделе.

Циклы в самом графе (A импортирует B, B импортирует A) не приводят к бесконечному обходу: каждая «нить» обхода помнит свой собственный путь от старта и не заходит на узел, который на этом пути уже был. Так как SQL не позволяет держать единый общий «список посещённого» внутри одного рекурсивного запроса, дедупликация «одного и того же узла, до которого дошли двумя разными путями» происходит уже в Rust-коде после запроса.

11 Долгие обходы: resume-токен

Если обрезка произошла из-за общего бюджета исследования (не глубины и не ветвистости одного узла — а просто «мы уже посмотрели достаточно строк за один вызов»), продолжить обычной постраничной выборкой нельзя: бюджет тратится сразу на весь обход, а не на один узел. Для этого случая ответ несёт непрозрачный resumeToken — закодированное «состояние обхода», которое агент присылает обратно на следующем вызове. 

sequenceDiagram
    participant Agent as Агент
    participant Core as Ядро

    Agent->>Core: get_dependencies(файл, depth=10)
    Core->>Core: обход упёрся в бюджет (5000 строк)
    Core-->>Agent: результаты + resumeToken (что уже видели)
    Note over Agent,Core: агент решает продолжить
    Agent->>Core: get_dependencies(resumeToken=...)
    Core->>Core: пересеять запрос всем «уже видели»,
продолжить с новым бюджетом
    Core-->>Agent: новые результаты + новый resumeToken (или конец)

Почему нельзя запомнить только «последнюю страницу»

Здесь и была настоящая инженерная тонкость. Когда обход возобновляется, нужно «пересеять» с той же границы (frontier), с которой остановились — но граничный узел на возобновлении снова предлагает все свои исходящие связи, а в первый раз система могла успеть отдать только часть из них. Если бы фильтр отсеивания дублей проверялся по узлу («мы уже были в этом узле — пропускаем всё, что из него ведёт»), часть связей терялась бы навсегда и без предупреждения. Поэтому фильтр стоит на уровне конкретного ребра: узел-граница разрешено переоткрыть, но конкретное ребро, которое уже было отдано, — нет. Это и есть причина, по которой состояние обхода накапливается целиком с самого начала цепочки, а не только за последний шаг: чтобы корректно решить «эту связь уже отдавали или ещё нет», нужно помнить полный список того, что уже отдано, а не только последнюю порцию.

Побочный эффект — токен растёт, и что с этим сделали

Раз состояние накопительное, закодированный токен растёт с каждым вызовом цепочки — это не ошибка, а прямое следствие только что описанной гарантии корректности. На реальных идентификаторах узлов (32-символьные hex-хэши) один-единственный срез по стандартному бюджету (5000 узлов) уже даёт токен в сотни килобайт; на длинной цепочке возобновлений — до нескольких мегабайт. Это разбиралось отдельной задачей: реальный жёсткий предел передачи (64 МБ на сообщение) тут ни при чём — токен даже в худшем измеренном случае в разы меньше. Настоящая цена другая: этот токен обязан вернуть обратно вызывающая сторона — а вызывающая сторона в этой системе, как правило, ИИ-агент, который платит за каждый лишний байт из своего собственного контекстного окна. Поэтому токен сейчас дополнительно сжимается (gzip) перед кодированием в base64 — измеренное ускорение около 2,3 раза на реалистичных данных, без единого изменения в логике самого обхода.

Рассматривался и вариант «хранить не весь список, а что-то покомпактнее, из чего список можно восстановить» — и был сознательно отклонён: корректность пересева (описанная выше защита от потери рёбер) требует именно полной истории, урезание рискует вернуть тот самый баг с потерянными связями, ради исправления которого эта конструкция и была придумана.

Один якорь на четыре инструмента

Чтобы спросить «кто вызывает эту функцию», формально сначала нужно узнать id этой функции — иначе на что ссылаться. Раньше это означало обязательную пару вызовов: сперва find_definition, потом сам вопрос. Замер реального использования показал: если имя однозначно, это лишний круг общения, который не даёт ничего, кроме траты «хода». Поэтому четыре инструмента (find_references/callers/callees/implementations) теперь принимают либо symbolId, либо symbolName напрямую — по общему внутреннему механизму («якорь», anchor.rs), тому же самому, которым пользуется сам find_definition. Если имя неоднозначно (в реальном коде Excalidraw нашлось два разных getNonDeletedElements с одинаковым квалифицированным именем!) — инструмент не гадает и не объединяет кандидатов молча, а честно возвращает список кандидатов с пометкой ambiguous: true и настоящим id каждого — именно id, а не имя, потому что одинаковое имя само по себе не гарантирует уникальность повторного запроса.

Постраничность и уровень доверия к ответу

Все списочные ответы разбиты на страницы непрозрачным курсором (не числовым смещением — потому что фоновая переиндексация может сдвинуть или задвоить строки прямо во время постраничного чтения). Любой ответ, построенный на ребре графа, несёт два поля: resolved (прошло ли ребро окончательную склейку) и source (tree-sitter или в будущем ts-compiler) — так агент видит не только факт связи, но и насколько ей можно доверять.

13 Модель доверия и безопасность

Явное решение проекта — не строить песочницу уровня ОС для языковых плагинов (пространства имён, seccomp, App Sandbox — всё это оценено как несоразмерное усилие против модели угроз, которая и так эквивалентна «языковому серверу редактора, у которого открыт ваш проект»). Вместо этого — точечные, дешёвые меры:

  • Плагины никогда не подгружают точки расширения вида tsconfig.json → compilerOptions.plugins, которые исполняют код при старте языкового сервера — известный вектор атаки через вредоносный конфиг. Для индексации это и не нужно, так что вектор просто не появляется.
  • Плагины не имеют прямого доступа на запись в индекс — пишет только ядро, плагин лишь присылает разницу по протоколу.
  • Доступ плагина к исходникам проекта — только на чтение.

14 Что задумано, а что пока не построено

Архитектурный документ описывает целевую систему; часть механизмов уже реализована и работает, часть — написана и покрыта тестами, но ещё не подключена к рабочему циклу, часть — пока только заложена в схему. Ниже — честная сверка, чтобы не создавать иллюзию, будто всё из плана уже работает.

15 Краткий словарь терминов

Узел / ребро (node / edge)
Узел — это символ (файл, функция, тип...). Ребро — связь между двумя узлами (вызывает, наследует, импортирует).
Заглушка (placeholder)
Временный узел на месте того, что плагин ещё не смог однозначно определить — например, куда ведёт импорт. Позже либо «дошивается» до настоящего узла, либо остаётся заглушкой навсегда, если цели действительно нет в индексе.
Резолвинг (resolve)
Процесс превращения строки-специфайера импорта («./utils», «@/lib») в конкретный путь к файлу.
Склейка (linking)
Отдельный проход ядра, который перецепляет ребро с заглушки на настоящий узел, когда тот появляется в индексе.
Курсор / resume-токен
Оба — непрозрачные строки для продолжения большого ответа. Курсор — для простой постраничной выборки; resume-токен — для продолжения обхода графа, несёт с собой состояние самого обхода.
WAL (Write-Ahead Log)
Режим SQLite, где изменения сначала пишутся в отдельный журнал, а потом сливаются с основным файлом — так чтение не блокируется параллельной записью.
Составлено по докам архитектуры (docs/architecture/g-mesh-v1.md) и коду репозитория g-mesh по состоянию на релиз 0.3.0 (Rust-ядро core/ + плагин plugins/js-ts/).
