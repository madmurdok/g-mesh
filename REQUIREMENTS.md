# g-mesh — требования к проекту

Рабочий документ для сбора требований. По нему будет составляться архитектура.
Статус: черновик, требования дополняются по ходу обсуждения.

## Идея

Локальный индексатор исходного кода проекта, который подключается к AI-агенту
по MCP и даёт агенту точное понимание структуры и связей в коде (кто кого
вызывает, где что определено, что от чего зависит), вместо того чтобы агент
угадывал это по grep/чтению файлов вручную.

## Ключевые требования

- **Индексация исходников**: программа подключается к проекту и строит индекс
  кодовой базы.
- **Интеграция по MCP**: индекс доступен AI-агенту как MCP-сервер/инструмент —
  агент обращается к нему при необходимости понять связи в коде.
- **Инкрементальное обновление**: при правках в коде должна быть возможность
  переиндексировать отдельные изменённые фрагменты, без полной переиндексации
  всего проекта.
- **Standalone-продукт**: индексатор работает без обращения к внешнему AI —
  сам процесс индексации и построения графа связей не зависит от LLM.
- **Локальный запуск**: предполагается запуск на машине разработчика
  (локальный процесс/сервис), без обязательной облачной инфраструктуры.

## Нефункциональные требования

Вынесено из решений ниже в одно место — не новые требования, а синтез уже
принятого. Ссылки — на разделы, где содержится полное обоснование.

**Производительность и масштабируемость**
- Холодный старт быстрый: tree-sitter-слой даёт рабочий граф почти сразу,
  семантика досчитывается асинхронно (см. "Первый языковой плагин",
  "Производительность/лимиты" п.1).
- Инкрементальный репарсинг — доли мс – единицы мс на правку (tree-sitter).
- Latency транзитивных graph-запросов — measurable порог p95 ~200–300мс как
  триггер миграции на Kùzu (см. "Формат хранения индекса").
- Bulk-изменения (`git checkout`/`pull`) батчатся в одну SQLite-транзакцию,
  не по файлу за раз (см. "Производительность/лимиты" п.4).
- Целевой масштаб — монорепы с сотнями тысяч файлов (лимиты inotify,
  партиционирование по границам проекта — см. "Производительность/лимиты").
- **Холодный tree-sitter-проход по монорепу ~100k файлов (~1–2 ГБ
  исходников) — не больше 2 минут** на типичном многоядерном ноутбуке
  разработчика (8+ ядер), при параллельном парсинге файлов по ядрам.
  Ориентир по порядку величины (tree-sitter даёт десятки МБ/с на ядро даже
  на сложных грамматиках вроде TS/JSX), не результат замера — подтвердить
  на прототипе, как и p95-порог миграции на Kùzu и выбор embedding-модели.
  Пересмотреть подход к параллелизации/прогреву, если промах будет не в
  разы, а на порядок.

**Потребление ресурсов**
- Embedding-модель: 100–500M параметров, footprint < 1 ГБ, CPU без GPU
  (см. "Embedding-модель для локального запуска").
- Core — один бинарник, без рантайм-зависимости для пользователя
  (см. "Язык имплементации core").
- Idle-дисциплина демона: тяжёлый процесс плагина засыпает по короткому
  таймауту (**`plugin.idleTimeoutMinutes`, дефолт — 1 час**: переживает
  типичные короткие паузы без дорогого повторного прогрева tsserver, но
  освобождает память на реально длинных простоях), лёгкое ядро — по
  гораздо более длинному (`daemon.coreIdleTimeoutHours`, дефолт 24ч) —
  ограничивает накопление OS-ресурсов (inotify-вотчеры, сокеты) при работе
  с многими проектами (см. "MCP-транспорт и lifecycle"). Оба числа —
  ориентиры, подтвердить эмпирически.
- Дисковое потребление ограничено через GC с предупреждением по умолчанию,
  явные команды для удаления (см. "Уборка неиспользуемых проектов").

**Приватность и безопасность**
- Standalone: индексация и построение графа не зависят от внешнего AI/LLM
  (см. "Ключевые требования").
- Содержимое проекта не покидает машину ни в одной дефолтной конфигурации,
  исключения только через явный opt-in (см. "Privacy/telemetry-позиция").
- Telemetry отсутствует в v1.
- Sandboxing плагинов: без исполняемых точек расширения из конфигов
  проекта, без лишнего сетевого доступа, минимальные права на запись
  (см. "Безопасность/sandboxing плагинов").
- MCP-трафик исключительно локальный (stdio+shim, не сетевой сервис).

**Надёжность и целостность данных**
- Никакой тихой отдачи устаревших данных — `resolved`/`source`,
  `hasSyntaxErrors`, `stale`, `indexCoverage` явно сообщают степень доверия
  к ответу (см. "Формат MCP-инструментов", "Обработка синтаксических
  ошибок", "Инвалидация эмбеддингов").
- Деструктивные операции (GC) по умолчанию предупреждают, не удаляют;
  массовое удаление требует явного `--force`.
- Стратегия keep-last-good при живом редактировании избегает
  ложноотрицательных "символа больше нет" на основе артефакта тайминга
  сохранения (см. "Обработка синтаксических ошибок").
- Задел на централизованную обработку ошибок для будущих crash-репортов без
  утечки содержимого кода (см. "Privacy/telemetry-позиция").
- **Неожиданный краш процесса-плагина** (паника, OOM-killer — в отличие от
  намеренного усыпления по idle-таймауту) обрабатывается тем же
  механизмом, что и пробуждение после сна: core детектирует неожиданное
  завершение и лениво перезапускает плагин при следующей необходимости,
  докатывая из очереди "грязных" файлов — не оставляет индексацию тихо
  сломанной до ручного вмешательства (`g-mesh stop`/`reindex`).
- **Durability записи в SQLite**: транзакционная запись (WAL mode) — краш
  ядра посреди операции никогда не оставляет индекс в повреждённом
  состоянии, требующем ручного ремонта; максимум теряется незакоммиченная
  транзакция, что безопасно (индекс — воспроизводимый кэш, источник истины
  — код на диске).

**Расширяемость и поддерживаемость**
- Языконезависимая схема графа с самого начала, даже при одном плагине в v1
  (см. "Схема графа", "Мультиязычность: core + языковые плагины").
- Механизм обнаружения/загрузки плагина — общий/pluggable уже в v1, несмотря
  на единственный бандленный путь (см. "Установка/дистрибуция языковых
  плагинов").
- Поле версии эмбеддинга заложено в схему с v1, хотя смена модели не
  поддерживается — избегает будущей миграции схемы (см. "Инвалидация
  эмбеддингов").
- **Conformance-тесты плагина** — общий набор фикстур/golden-файлов,
  которым должен соответствовать любой плагин (первого или стороннего
  производства), проверяющий соответствие протоколу core↔плагин (корректные
  kind/типы рёбер, валидный NDJSON-фрейминг) — не полноту покрытия языка.
  Без этого регрессия в плагине может тихо испортить граф незаметно для
  core.
- **Несовпадение версии протокола core↔плагин — отказ загрузки с понятной
  ошибкой**, не best-effort совместимость. Для v1 неактуально (бандленные
  core и плагин всегда синхронны), но важно для расширяемости на будущие
  (в т.ч. сторонние) плагины — по аналогии с версией схемы графа (там —
  полный реиндекс при несовпадении, здесь — отказ загрузки, потому что
  "переиндексировать" протокол не значит ничего, это код, не данные).

**Совместимость**
- Кроссплатформенный file watching (inotify/FSEvents/ReadDirectoryChangesW
  через `notify`).
- MCP-стандартный транспорт (stdio) — совместимость с любым MCP-клиентом
  без кастомной интеграции (см. "MCP-транспорт и lifecycle").
- **IPC shim↔демон — `AF_UNIX`-сокеты везде, включая Windows** (нативная
  поддержка с Windows 10 build 17063+ / Server 2019+, через
  Rust/tokio — единый механизм на все ОС, без platform-conditional кода).
  Явно фиксирует **минимальную поддерживаемую версию Windows** — раньше
  этого ограничения нигде не было, хотя Windows-поддержка уже подразумевалась
  (`ReadDirectoryChangesW` для watcher, обработка CRLF в протоколе
  core↔плагин).

**Юзабилити**
- Zero-config для основного сценария — агент просто конфигурируется на
  spawn-команду, shim сам находит/поднимает нужный демон по проекту.
- Интерактивный wizard (`g-mesh config`) вместо ручного написания TOML для
  типовых настроек.
- CLI-only в v1 — осознанное решение по объёму UX-скоупа, GUI — самый
  низкий приоритет (см. "UI").
- **Установка — install-скрипт (`curl | sh`) с бинарниками из GitHub
  Releases для v1.** npm-обёртка (`npm install -g g-mesh`, привычнее для
  целевой JS/TS-аудитории, паттерн esbuild/swc/Biome) — кандидат на
  будущее, не блокирует v1.
  - Архитектурное условие на будущее (не переделка, а требование к
    релизному пайплайну уже сейчас): бинарники публикуются в GitHub
    Release **чётко именованными под каждую платформу** по стандартным
    Rust target triples (`g-mesh-x86_64-apple-darwin`,
    `g-mesh-aarch64-apple-darwin`, `g-mesh-x86_64-unknown-linux-gnu`,
    `g-mesh-x86_64-pc-windows-msvc` и т.п.) — тот же набор артефактов
    переиспользуется без изменений, если позже добавится npm-обёртка
    (`optionalDependencies` на платформенные пакеты).
  - Плагин (self-contained Node SEA/bun-бинарник) попадает в тот же
    архив/релиз под ту же платформу — не зависит от способа установки.
  - Install-скрипт проверяет checksum скачанного бинарника перед
    установкой — стандартная гигиена для curl|sh-паттерна.

## Открытые вопросы / решения по ходу обсуждения

### Алгоритм индексации: граф vs вектора
Решение (подтверждено): гибридный подход. Формулировка "предварительное"
осталась с первого раунда обсуждения — с тех пор больше 20 последующих
решений (схема графа, MCP-инструменты, формат хранения, `resolved`/`source`
на рёбрах, разделение `search_code` от структурных инструментов) строились
поверх этого гибрида и ни разу не вскрыли повод его пересмотреть.
- **Граф** — источник истины для точных структурных связей (символы, вызовы,
  импорты, типы). Строится статическим анализом (tree-sitter / LSP).
- **Векторные эмбеддинги** — слой поверх узлов графа для семантического
  поиска по смыслу, когда агент не знает точных имён символов.

Trade-off: граф точен, но дороже в разработке (парсер под каждый язык,
инкрементальная переиндексация). Вектора дешевле и языконезависимы, но
ненадёжны на структурных вопросах.

Референсы для изучения: Sourcegraph SCIP, aider repo-map (tree-sitter +
PageRank по графу вызовов).

### Embedding-модель для локального запуска
Локально практичнее лёгкая/средняя код-специфичная модель (100–500M
параметров, footprint < 1 ГБ), работает на CPU без GPU. Крупные модели
(1B+) точнее, но требуют GPU и обычно доступны только через API — не подходят
под требование standalone/локального запуска.

Кандидаты: bge-small / gte-small (лёгкие, общего назначения),
jina-embeddings-code / nomic-embed-code (средние, код-специфичные).

**Дефолтная модель для v1 — `jina-embeddings-v2-base-code`.** Причины:
единственный кандидат, обученный именно на парах "код + описание на
естественном языке" — ровно паттерн, нужный `search_code` (поиск кода по
смыслу текстового запроса); компактный (~160M параметров, укладывается в
рамки 100–500M/<1ГБ); обучен на ~30 языках — задел на будущую
мультиязычность, не привязан к JS/TS; длинный контекст (до 8192 токенов) —
с запасом на сигнатуру+докстринг; Apache 2.0, не блокирует дистрибуцию.

Оговорка: архитектурная рекомендация, не результат бенчмарка на реальном
коде — перед жёсткой фиксацией в `meta.embedding_model` стоит проверить
эмпирически на прототипе (тот же процесс, что уже заложен для порога
миграции на Kùzu в разделе "Формат хранения индекса").

### Мультиязычность: core + языковые плагины
Решение: расширяемая архитектура — **core** определяет универсальную схему
графа и контракт плагина (что плагин обязан отдавать: узлы/рёбра в общем
формате). Языковые плагины — **отдельные процессы**, общающиеся с core по
простому протоколу в духе LSP, а не встроенные библиотеки в общем рантайме.

Это позволяет каждому плагину использовать нативный тулинг своего языка
(например, для TS — обёртку над TypeScript compiler API вместо парсинга
tree-sitter'ом), что даёт точную семантику (типы, разрешение перегрузок), а
не только синтаксис.

Trade-off: процессная модель усложняет управление (много запущенных
языковых серверов, IPC-оверхед на инкрементальных правках) по сравнению с
альтернативой — все языки через tree-sitter грамматики in-process (проще в
эксплуатации, но даёт только синтаксический граф без семантического
разрешения).

Референс: похожая модель у Sourcegraph (core + SCIP-индексаторы на язык).

### Первый языковой плагин: JavaScript/TypeScript + JSX/TSX
Решение: первая реализация — плагин для JS/TS/JSX/TSX (основной стек).
Плагин — процесс на Node.js.

Парсинг внутри плагина — **гибридный, двухслойный**:
- **tree-sitter** (`tree-sitter-typescript`/`tree-sitter-javascript`) —
  быстрый структурный слой. Инкрементальный репарсинг только изменённого
  поддерева (доли мс – единицы мс на правку), даёт черновой граф (границы
  функций/классов, вызовы по имени) без разрешения типов.
- **TypeScript compiler API** (или `tsserver`) — точечно, только там, где
  синтаксического разбора недостаточно (перегрузки, реэкспорты, динамические
  импорты, разрешение типов). Дороже по CPU (десятки–сотни мс, каскадная
  инвалидация зависимых файлов), поэтому не гоняется на каждую правку целиком.

Причина: чистый tsserver/TS compiler API на каждую правку — слишком дорого
на больших проектах (правка в часто импортируемом файле может заставить
перепроверить много зависимых файлов). tree-sitter даёт мгновенный отклик,
TS compiler API вызывается асинхронно/точечно для уточнения семантики.

`tsserver` уже работает в формате, близком к LSP — это же валидирует
протокол core ↔ плагин, намеченный выше.

### Протокол core ↔ языковой плагин
Решение: транспорт — **stdio**, два формата сообщений в зависимости от типа
обмена.

- **Control-слой** (запросы/уведомления: «переиндексируй файл X», «файл Y
  изменился», статус) — **JSON-RPC 2.0** с LSP-style фреймингом
  (`Content-Length` заголовок + JSON-тело). Тот же формат, что LSP и
  `tsserver`-протокол — плагин на tsserver ложится почти без адаптера.
- **Bulk-передача графа** (первичная полная индексация — массовая отдача
  узлов/рёбер) — **NDJSON**: один compact JSON-объект на строку, без
  embedded raw newlines (перевод строки внутри значения экранируется
  сериализатором как `\n`, конфликта с построчным разделителем нет).
  Позволяет core поглощать данные потоково, не буферизуя весь батч, и не
  теряет весь батч при одной битой записи.

Инкрементальное обновление: core уведомляет плагин об изменённом файле →
плагин пересчитывает только его → отдаёт diff (добавленные/удалённые узлы и
рёбра), а не весь граф заново.

Ограничения к учесть в реализации: продюсер обязан отдавать компактный
(однострочный) JSON на запись; парсер на core должен подрезать `\r` (CRLF на
Windows) и не иметь фиксированного лимита длины строки.

**Конформность плагина и версионирование протокола**:
- **Conformance-тесты** — общий набор фикстур/golden-файлов, которым
  должен соответствовать любой плагин (первого или стороннего
  производства), проверяющий соответствие именно протоколу (корректные
  kind/типы рёбер, валидный NDJSON-фрейминг), не полноту покрытия языка.
  Без этого регрессия в плагине может тихо испортить граф незаметно для
  core.
- **Несовпадение версии протокола core↔плагин — отказ загрузки плагина с
  понятной ошибкой**, не best-effort совместимость. Для v1 неактуально
  (бандленные core и плагин всегда синхронны), важно на будущее для
  расширяемости (см. "Установка/дистрибуция языковых плагинов") — по
  аналогии с версией схемы графа (там — полный реиндекс при несовпадении,
  здесь — отказ загрузки, потому что протокол это код, не данные,
  "переиндексировать" его не имеет смысла).

### Формат хранения индекса
Решение: **SQLite + `sqlite-vec`** — один embedded движок и для графа, и для
векторов, один файл на диске, без отдельного сервиса.

- Узлы/рёбра графа — обычные таблицы с индексами, обход через recursive CTE
  (многошаговые запросы вида «кто кого вызывает транзитивно»).
- Векторный поиск — расширение `sqlite-vec` в той же базе.

Причина выбора именно SQLite (против DuckDB/LanceDB): основной паттерн
нагрузки — частые мелкие инкрементальные записи (правка файла → апдейт
горстки строк), это классический OLTP-паттерн, под который SQLite и заточен.
DuckDB — OLAP/колоночный движок, силён на bulk-аналитике, но не на частых
мелких транзакциях. LanceDB — сильный чистый vector store, но без графового
query-языка вообще, потребовал бы держать граф в отдельном движке (два
хранилища вместо одного).

Trade-off: recursive CTE в SQLite менее эргономичны и медленнее нативного
графового движка (напр. embedded Kùzu с Cypher-подобными запросами) на
глубоких многошаговых обходах.

**Уточнение (согласовано с лимитом глубины обхода в разделе
"Производительность/лимиты")**: response-лимиты (`maxDepth`/`maxFanout`,
пагинация) ограничивают только то, что возвращается агенту, но не то,
сколько узлов recursive CTE физически обойдёт внутри запроса — на хабовом
узле движок может провалиться в комбинаторный перебор ещё до обрезки
пагинацией. Нужен отдельный **internal exploration-бюджет** — жёсткий
`LIMIT` внутри самого recursive CTE на общее число посещённых строк,
независимо от `maxDepth`/`maxFanout` и от того, что попадёт в ответ.

**Дефолтные числа** (ориентир, подтвердить на прототипе, как и остальные
числа в этом документе):
- `maxDepth = 5` — глубже практическая релевантность для агента обычно уже
  теряется, а потенциальный размер результата резко растёт.
- `maxFanout = 50` — сколько дочерних рёбер разворачивать с одного узла на
  каждом уровне обхода.
- Internal exploration-бюджет = **5000 посещённых узлов** на весь запрос —
  реальная защита от комбинаторного взрыва на хабовом узле, отдельно от
  `maxDepth`/`maxFanout`.

**Худший сценарий — обход обрезан лимитом до того, как реально нашёл всё
нужное** (легитимно длинная цепочка вызовов глубже 5 хопов, легитимно
широкий fanout на популярной утилите, или бюджет исчерпан на хабовом узле
раньше, чем обход дошёл до нужной ветки). Риск не в самой неполноте, а в
том, что она может выглядеть как "результатов больше нет" — прямое
нарушение принципа "никакой тихой отдачи неполных данных" (см.
`resolved`/`stale`/`indexCoverage` в других разделах). Поэтому:

- Ответ обязан нести **`truncated: true`, `truncatedBy: 'maxDepth' |
  'maxFanout' | 'explorationBudget'`**, когда обход остановлен лимитом, а
  не потому что данных больше нет.
- **Механизм продолжения зависит от типа truncation**, не один
  универсальный:
  - `maxFanout` — новая инфраструктура не нужна: ответ называет узел, на
    котором обрезано, агент делает обычный однохоповый запрос
    (`find_callers`/`find_references`) с уже существующей cursor-пагинацией
    на этот узел.
  - `maxDepth` — ответ содержит **`frontierNodes`** (узлы на границе
    глубины, последний развёрнутый уровень); агент перезапускает тот же
    обходной инструмент, взяв frontier-узел новым корнем — семантически
    "на уровень дальше", без специального токена.
  - `explorationBudget` — единственный случай, где нужен новый механизм:
    бюджет тратится на весь обход разом, не привязан к одному узлу, рестарт
    с нуля упрётся в тот же бюджет в том же порядке. Ответ несёт
    **`resumeToken`** (непрозрачный, кодирует посещённые узлы + очередь
    фронтира — тот же принцип, что `cursor` в обычной пагинации, только для
    состояния обхода). Повторный вызов с `resumeToken` продолжает обход со
    свежим бюджетом с того места, где остановился.

Конкретный, измеримый триггер миграции на Kùzu (вместо расплывчатого "если
обходы станут узким местом"): когда появится рабочий прототип хранилища —
прогнать бенчмарк на синтетическом графе, приближённом к большому монорепо
(сотни тысяч узлов, синтетический hub-узел с тысячами связей), с
exploration-бюджетом на потолке. Если p95 латency такого запроса превышает
~200–300мс (порог, при котором задержка MCP-инструмента станет заметна) —
мигрировать графовую часть на Kùzu, оставив вектора в SQLite.

### Схема графа
Решение: гранулярность — **уровень символов** (не файл целиком — слишком
грубо для запросов вида "кто вызывает функцию X"; не каждое
выражение/statement — слишком мелко, раздувает индекс). Локальные переменные
внутри тела функции в граф не попадают.

Важное ограничение: схема должна быть **языконезависимой** — она общая для
core, а конкретные языковые плагины (JS/TS сейчас, другие языки в будущем)
маппят свои конструкции в неё. Раздельные `Class`/`Interface` и
`Extends`/`Implements` были бы JS/TS-центричны и не легли бы на языки без
классов (Go, Rust с трейтами и т.п.) — поэтому специфика языка вынесена в
отдельное escape-hatch поле, а не в основной enum типов.

**Kind узлов** (одна таблица `nodes` с полем `kind`):
- `File`
- `Module` — namespace/package/крейт, единица группировки
- `Type` — покрывает class/interface/struct/trait/enum
- `Function` — покрывает function/method
- `Variable` — только модульного уровня/экспортируемая

Атрибуты узла: `id` (стабильный между правками — нужен для инкрементального
diff), `kind`, `name`, `qualifiedName`, `filePath`, `range` (start/end
line-col), `signature` (для функций), `exported`, JSDoc/комментарий
(пригодится как текст для эмбеддинга), **`language`** (какой плагин породил
узел), **`nativeKind`** (language-specific уточнение: `"trait_impl"`,
`"protocol"`, `"struct"` и т.п. — не участвует в универсальном обходе графа).

**Типы рёбер**:
- `DEFINES` (File → Symbol)
- `IMPORTS` (File → File/Symbol)
- `CALLS` (Function → Function)
- `SUPERTYPE_OF` — обобщённый тип вместо раздельных `EXTENDS`/`IMPLEMENTS`,
  покрывает наследование класса, реализацию интерфейса, `impl Trait`,
  структурную типизацию — что угодно, что плагин сочтёт "является
  подтипом/реализацией"
- `REFERENCES` (общее использование символа)
- `EXPORTS` (File → Symbol)

На ребре — поле **`source: 'tree-sitter' | 'ts-compiler'`** (в общем виде —
`resolved: bool`), вытекает из решения про гибридный парсинг: tree-sitter
даёт связи по имени (эвристика, может ошибаться на перегрузках/реэкспортах),
семантический слой плагина их подтверждает/уточняет точечно. Без этого поля
core не отличит точно установленную связь от вероятной.

Референс: похожий подход у SCIP (Sourcegraph) — минимальная универсальная
схема + language-specific детали вынесены отдельно.

### Язык имплементации core
Решение: **Rust**. Приоритет — долгосрочный результат и производительность,
не скорость итерации на MVP.

Причины:
- `tree-sitter` нативно на Rust (first-class биндинги, тот же фундамент, что
  у Zed/Helix/ast-grep).
- Дистрибуция одним бинарником — standalone-требование выполняется без
  рантайм-зависимости для пользователя (плагины типа Node.js — деталь
  реализации конкретного языкового плагина, а не то, что ставит пользователь
  отдельно для core).
- Зрелые биндинги `rusqlite` под SQLite, `sqlite-vec` грузится как обычное
  расширение.
- MCP SDK под Rust (`rmcp`) существует, хоть и менее обкатан, чем
  официальный TS SDK.

Trade-off, принятый осознанно: скорость итерации на схеме/протоколе ниже,
чем была бы на TS — графы с общими ссылками между узлами исторически
неудобны в Rust (borrow checker), обычно решается через arena/индексы вместо
указателей. Локальная embedding-модель через ONNX (`ort` crate) рабочая, но
менее plug-and-play, чем в Python/JS-экосистемах. Осознанно принимаем эту
цену ради производительности и простоты дистрибуции в долгосрочной
перспективе.

### Формат MCP-инструментов
Решение: набор **целевых инструментов** под конкретные задачи, а не один
generic "выполни graph-запрос" — агент плохо пишет query-языки вслепую, зато
умеет уверенно вызывать `find_callers(id)`.

Набор для MVP:

| Инструмент | Вход | Что возвращает |
|---|---|---|
| `find_definition` | имя символа или `file+position` | узел: kind, signature, docstring, location |
| `find_references` | `symbolId` | места использования (edges `REFERENCES`) |
| `find_callers` | `symbolId` | кто вызывает функцию (обратные `CALLS`) |
| `find_callees` | `symbolId` | что вызывает функция |
| `find_implementations` | `symbolId` | кто реализует/наследует тип (обратные `SUPERTYPE_OF`) |
| `search_code` | текстовый запрос | семантический поиск по эмбеддингам |
| `get_file_outline` | `filePath` | список символов, определённых в файле |
| `get_dependencies` | `filePath`/`moduleId` + направление | импакт-анализ перед правкой |

**Пагинация — cursor-based, а не жёсткий limit с обрезкой**:
- Ответ содержит `results` (текущий батч), `hasMore: bool`, `nextCursor`
  (непрозрачный токен для продолжения).
- Агент получает батч → если нужного нет, вызывает тот же инструмент с
  `cursor: nextCursor` → следующий батч.
- Cursor, а не `offset` — устойчивее к изменению графа между вызовами
  (переиндексация в фоне может сдвинуть/задвоить записи при offset-пагинации).
- Размер батча небольшой по умолчанию (экономия контекста агента), точное
  число — эмпирически при тестировании.

Порядок результатов внутри батча должен быть релевантным, иначе батчинг
бесполезен:
- `search_code` — по similarity score (естественно для vector search).
- Структурные инструменты (`find_references`/`find_callers` и т.п.) —
  сначала рёбра с `resolved: true` (подтверждено семантическим слоем), затем
  `resolved: false` (эвристика tree-sitter); внутри группы — близость
  (тот же модуль/файл раньше дальних).

Инструменты обязаны прокидывать поле `resolved`/`source` в ответе, чтобы
агент понимал степень доверия к конкретной связи.

**`find_definition` при неоднозначном имени символа** — вход "имя символа"
(без `file+position`) может соответствовать нескольким узлам сразу (схема
графа отдельно вводит `qualifiedName` именно для такого различения).
Поведение: инструмент возвращает **список кандидатов** через тот же
cursor-пагинация контракт, что и остальные инструменты — не ошибку и не
единственный "угаданный" результат. Каждый элемент несёт `qualifiedName`,
`filePath`, `kind`, превью `signature`/докстринга. Сортировка — по числу
входящих `REFERENCES`/`CALLS`-рёбер (убывание), тот же принцип
релевантности, что и у остальных инструментов, переиспользует уже
существующие данные графа. Уточняющий повторный вызов с полученным
`qualifiedName` даёт точный, не эвристический результат. Вход
`file+position` всегда однозначен — список не оборачивается, возвращается
ровно один узел.

### Триггер переиндексации
Решение: **гибрид — file watcher как основной триггер + query-time staleness
check как safety net**. Git hook не используется.

- **File watcher** — fs-события (inotify/FSEvents/ReadDirectoryChangesW,
  кроссплатформенно через `notify` crate), core живёт как фоновый процесс.
  Debounce на быстрые повторные события (автосейв редактора/форматтер могут
  дать несколько write-событий на один файл). Уважает `.gitignore` —
  `node_modules`, `dist`, `.git` и т.п. не индексируются.
- **Query-time staleness check** — перед ответом на MCP-запрос core сверяет
  mtime/hash файла с проиндексированным; при расхождении (watcher мог
  пропустить событие — сетевые диски, WSL иногда теряют fs-события)
  переиндексирует synchronously перед ответом. Дешёво благодаря скорости
  tree-sitter-слоя (доли мс – единицы мс), гарантирует отсутствие тихой
  выдачи устаревших данных.

Git hook (pre-commit/post-commit) отклонён как основной триггер: агент
работает в первую очередь с незакоммиченными правками — hook сработает
только на коммите, то есть именно тогда, когда актуальность индекса уже не
критична для текущей задачи.

### MCP-транспорт и lifecycle
Решение (пересмотрено): **stdio-транспорт + shim-процесс с авто-бутстрапом
демона**. Более раннее решение (чистый Streamable HTTP, без shim)
отклонено — см. причину ниже.

Схема:
- MCP-клиент спавнит `g-mesh mcp-shim` как обычный stdio-сервер, с `cwd`
  текущего проекта — это его штатное поведение, ничего специального не
  требуется.
- Shim по пути проекта вычисляет идентификатор (хэш пути) и проверяет,
  запущен ли демон для этого проекта (`~/.g-mesh/projects/<hash>/`). Если
  нет — стартует его сам (detached-процесс, переживает завершение shim).
  Если да — подключается к его unix-сокету.
- Shim — чистый прокси: перепаковывает JSON-RPC из stdio-фрейминга в
  сокет-фрейминг демона и обратно, без собственной логики.
- Гонка при параллельном первом старте (несколько shim на один проект
  одновременно) — файловый лок на pid/сокет-файл демона.
- **IPC-механизм — `AF_UNIX`-сокеты везде, включая Windows** (нативная
  поддержка с Windows 10 build 17063+ / Server 2019+, через Rust/tokio —
  единый механизм на все ОС, без platform-conditional кода). Явно
  фиксирует минимальную поддерживаемую версию Windows.

Почему пересмотрено (изначально был выбран чистый HTTP без shim, см.
причины отказа в истории обсуждения): в HTTP-варианте демон должен либо
жить вечно (расход ресурсов на каждый открытый проект), либо
останавливаться по idle-таймауту — но тогда агенту не к чему
переподключиться (порт больше не слушается, а спавнить процесс при чистом
HTTP-транспорте некому). Это потребовало бы держать HTTP-listener всегда
живым и городить ленивое пробуждение внутренностей + staleness catch-up как
обязательный путь — сложнее, чем просто дать MCP-клиенту делать то, что он
и так умеет (спавнить процесс по требованию).

С shim'ом это решается естественно: если демон **вообще не запущен** (первый
запуск, после перезагрузки машины, ручная остановка) — shim поднимет его
заново с нуля, это тот же холодный старт, что и при первой индексации.

**Уточнение по idle-таймауту (пересмотрено после разбора находки про
повторную регистрацию file watcher)**: полностью гасить *весь* демон по
idle-таймауту оказалось слишком грубо — единица, которую мы называли
"демон", на деле состоит из двух разных по стоимости частей:

- **Лёгкое ядро демона** — сам процесс `g-mesh`, file watcher (см. "Триггер
  переиндексации"), SQLite-хэндл, слушатель unix-сокета для shim. Не
  гасится по короткому idle-таймауту — живёт, пока не остановлен явно
  (`g-mesh stop`), машина не перезагрузится, или не истечёт **отдельный,
  гораздо более длинный таймаут самого ядра** (см. ниже). Регистрация
  fs-вотчеров (см. лимиты inotify в "Производительность/лимиты", п.3)
  происходит один раз за время жизни ядра, а не на каждом цикле "агент
  помолчал → снова спросил".
- **Процесс языкового плагина** (Node.js, у JS/TS-плагина в одном процессе
  живут и tree-sitter, и TS compiler API — см. "Первый языковой плагин") —
  вот его и гасим по idle-таймауту (**`plugin.idleTimeoutMinutes`, дефолт
  — 1 час**: переживает типичные короткие паузы без дорогого повторного
  прогрева tsserver, но освобождает память на реально длинных простоях),
  он реально тяжёлый по памяти/CPU. Пока плагин выключен, ядро продолжает
  получать fs-события и копит очередь "грязных" файлов, не пытаясь их
  обработать. При пробуждении плагина (по первому запросу, которому он
  нужен) — не полный рескан проекта, а докатка только из этой очереди.

**Защита от накопления висящих ядер (отдельная проблема от GC)**: GC (см.
"Уборка неиспользуемых проектов") чистит только диск — кэш/конфиг
неиспользуемых проектов, но не трогает уже запущенные процессы. Если за
долгое время (без перезагрузки машины) потрогать много разных проектов,
каждый получит своё вечно живое лёгкое ядро — inotify-вотчеры,
SQLite-хэндл, сокет на каждый. Решение — отдельный, гораздо более длинный
idle-таймаут для самого ядра: **`daemon.coreIdleTimeoutHours`** (per-project
конфиг, тот же принцип, что и `plugin.idleTimeoutMinutes` — личное
предпочтение для конкретного проекта), дефолт — 24 часа без единого
MCP-запроса. По истечении ядро завершается чисто (снимает вотчеры, закрывает
SQLite-хэндл, освобождает сокет); следующее обращение через shim — обычный
холодный старт, тот же code path, что при первом запуске.

Не противоречит решению не гасить ядро по короткому таймауту — там речь про
минуты простоя внутри одной рабочей сессии (частые паузы агента), здесь —
про часы/дни бездействия конкретного проекта, пока разработчик работает над
другими. Разные масштабы времени, разные цели.

Жёсткий лимит на число одновременно живых ядер (LRU-вытеснение) — кандидат
на будущее, если таймаута окажется недостаточно; не заводим сразу, чтобы не
усложнять ради непроверенной проблемы.

**Мульти-проектность** — из этой же схемы: каждый проект получает свой
демон (идентификация по хэшу пути, не по вручную сконфигурированному
порту), zero-config для пользователя — не нужен ни отдельный `g-mesh start`,
ни URL/порт в конфиге агента. Переключение клиента на другой проект → новый
`cwd` → shim сам находит/поднимает нужный демон.

**Где лежит индекс** — общий кэш `~/.g-mesh/projects/<hash>/`, не внутри
репозитория. Причины: не нужно добавлять в `.gitignore` (легко забыть), не
зависит от того, смонтирован ли репозиторий read-only/по сети, не мусорит в
директории пользователя, g-mesh может свободно чистить свой кэш
(`g-mesh clean`), не трогая репозиторий.

HTTP-транспорт как дополнительный (для клиентов без поддержки stdio, если
такие понадобятся) можно рассмотреть отдельным раундом после MVP — не
блокирует текущую архитектуру.

### Установка/дистрибуция языковых плагинов
Решение: для v1 плагин JS/TS **бандлится вместе с core** — один
инсталлятор ставит и core, и плагин, без отдельного шага
скачивания/`g-mesh plugin install`. Полноценный registry строится позже,
когда появится реальный второй плагин, а не заранее под гипотетический
случай.

Плагин компилируется в **самодостаточный исполняемый файл** (Node.js Single
Executable Applications / `bun build --compile`), не требует системного
Node.js у пользователя — прямое следствие standalone-принципа, забота
build/release-пайплайна, не архитектуры рантайма.

Важное уточнение (чтобы не упереться в переделку архитектуры при появлении
второго плагина): **механизм обнаружения и загрузки плагина core должен
быть общим/pluggable уже в v1**, даже если единственный используемый путь
сейчас — бандленный плагин. То есть core с самого начала обращается к
плагинам через единый интерфейс (директория `~/.g-mesh/plugins/<language>/`,
манифест с версией протокола), а бандлинг v1 — это просто способ туда
попасть, не единственный жёстко зашитый путь.

Заложить на будущее (не реализовывать в v1, но не блокировать
архитектурой):
- `g-mesh plugin install <language>` — установка из registry (когда он
  появится).
- **Установка плагина из локальной файловой системы** (`g-mesh plugin
  install --path ./my-plugin`) — для офлайн-установки, приватных/кастомных
  плагинов и локальной разработки/тестирования плагина без публикации в
  registry.

### Производительность/лимиты на больших монорепах

Пять требований, часть из них — общий контракт core↔плагин (языконезависимо),
часть — чисто core-уровня.

1. **Холодный старт — общий принцип для любого плагина**. Плагин с глубоким
   семантическим слоем (TS compiler API, `rust-analyzer`, `gopls` и т.п.)
   обязан отдавать быстрый синтаксический граф немедленно и досчитывать
   семантику асинхронно в фоне, не блокируя доступность индекса. Как именно
   плагин это реализует — его внутреннее дело (для JS/TS — уже решённый
   двухслойный tree-sitter + TS compiler API), но результат — часть
   контракта плагина с core. **Целевое время**: холодный tree-sitter-проход
   по монорепу ~100k файлов (~1–2 ГБ исходников) — не больше 2 минут на
   типичном многоядерном ноутбуке (8+ ядер), при параллельном парсинге по
   ядрам. Ориентир по порядку величины, не результат замера — подтвердить
   на прототипе.

2. **Партиционирование по границам проекта — тоже ответственность плагина**.
   У каждого языка своя единица модуля семантического анализа (JS/TS —
   `package.json`/`tsconfig.json`, Rust — члены Cargo workspace, Go —
   модули). Core этого не знает и не диктует — плагин сам определяет
   границы своего языка и пересчитывает семантику в этих границах, а не по
   всему репозиторию плоско.

3. **File watcher — лимиты ОС** (core-уровня). Linux inotify имеет лимит на
   число вотчеров (`fs.inotify.max_user_watches`) — на монорепе с
   десятками тысяч директорий можно упереться в лимит даже с исключённым
   через `.gitignore` `node_modules`. Нужен fallback (частичный polling)
   и лёгкая деградация вместо падения.

4. **Bulk-изменения** (core-уровня). `git checkout`/`git pull`, меняющий
   сотни файлов разом — реиндексация/запись в SQLite по одному файлу в
   отдельной транзакции даст неприемлемый I/O оверхед. Нужно детектировать
   всплеск изменений (много событий watcher'а за короткое окно) и
   оборачивать их в одну SQLite-транзакцию.

5. **Лимит глубины обхода графа** (core-уровня). Пагинация ограничивает
   ширину ответа, но не глубину — транзитивный обход (`find_callers`
   рекурсивно) на хабовом символе может улететь в комбинаторный взрыв.
   Нужен явный лимит глубины/fanout на транзитивных запросах, отдельно от
   пагинации списка. Это response-лимит (что видит агент) — отдельно от
   internal exploration-бюджета recursive CTE и триггера миграции на Kùzu,
   см. уточнение в разделе "Формат хранения индекса".

### Безопасность/sandboxing плагинов
Решение: без полноценного OS-level сендбоксинга в v1 (кроссплатформенная
работа большая — namespaces/seccomp на Linux, App Sandbox на macOS,
AppContainer на Windows — ради предельного случая, когда уровень доверия и
так равен "проект уже открыт в редакторе с LSP"). Вместо этого — дешёвые
точечные меры:

1. **Не подгружать точки расширения языкового тулинга, рассчитанные на
   исполнение кода** — например, игнорировать `tsconfig.json` → `plugins`
   (npm-пакеты, исполняемые при старте `tsserver`, известный вектор атаки
   через вредоносный `tsconfig.json`). Для индексации эта функциональность
   не нужна, пропуск убирает вектор бесплатно.
2. **Уточнено — плагину не нужен доступ на запись к индексу вообще.**
   По протоколу core ↔ языковой плагин (см. "Протокол core ↔ языковой
   плагин") плагин отдаёт изменения через NDJSON/JSON-RPC по stdio — в
   SQLite пишет исключительно core, плагин с индекс-директорией напрямую
   не взаимодействует. Периметр прав уже, чем формулировалось раньше:
   исходники проекта read-only с точки зрения плагина, доступ на запись —
   только собственные временные/лог-файлы плагина (если такие вообще
   нужны), не индекс/кэш-директория.
3. **Не давать плагину сетевых возможностей, не нужных для анализа** —
   усиливает уже принятый принцип "код не покидает машину"
   (архитектурное ограничение на уровне того, что плагин делает, не
   OS-level firewall).
4. **Явно документировать модель доверия** — плагин работает в той же
   доверительной зоне, что обычный language server в редакторе
   разработчика; не обещать пользователю безопасность, которой на деле нет.

Полноценный OS-level sandboxing — кандидат на будущее укрепление после MVP,
не блокирует архитектуру.

### Формат конфигурации проекта
Решение: **TOML**, файл `~/.g-mesh/projects/<hash>/config.toml` — рядом с
индексом, **не коммитится в git**.

Причины:
- TOML даёт комментарии нативно и парсится штатным крейтом `toml` в Rust —
  не нужен препроцессор для вырезания комментариев (как понадобился бы для
  JSONC).
- Конфиг не обязан выглядеть "как привычный JS-тулинг" (`tsconfig.json` и
  т.п.), потому что g-mesh, в отличие от них, **не влияет на сборку/общий
  для команды результат** — это личный локальный инструмент разработчика.
  Индекс не шарится между членами команды (каждый строит свой в
  `~/.g-mesh/`), поэтому и большинство настроек (таймаут простоя плагина
  `plugin.idleTimeoutMinutes`, таймаут ядра `daemon.coreIdleTimeoutHours`,
  выбор embedding-модели под своё железо, размер батча под свой контекст)
  — это личные предпочтения, а не то, что должно быть одинаковым у всей
  команды.

На будущее (не для v1, не блокирует архитектуру): если появится реальный
кейс для небольшого набора *project-level* фактов, полезных всей команде
(например "этому проекту нужен плагин X") — рассмотреть отдельный,
минимальный, опциональный in-repo файл. Не проектировать заранее без
конкретного случая.

**Заполнение конфига — через интерактивный wizard, не через `init`.**
Пересмотр: `init` и настройка — разные по смыслу команды, разводим их.

- **`g-mesh init`** — bootstrap проекта: создаёт структуру под
  `~/.g-mesh/projects/<hash>/`, пишет `config.toml` с разумными дефолтами
  (без интерактивных вопросов), запускает первичную индексацию. Опционален
  — zero-config путь и так работает (shim сам поднимает демон с дефолтами
  при первом обращении агента); `init` нужен тем, кто хочет сразу
  проиндексировать проект, не дожидаясь ленивого холодного старта на
  первый запрос агента.
- **`g-mesh config`** — интерактивный wizard (какие языки включить, выбор
  embedding-модели с коротким описанием trade-off "быстрее/точнее",
  **таймаут простоя плагина** — `plugin.idleTimeoutMinutes`, не "таймаут
  демона": после пересмотра lifecycle в разделе "MCP-транспорт и lifecycle"
  ядро демона не имеет idle-таймаута вообще, таймаут применяется только к
  процессу языкового плагина). Per-project по умолчанию (cwd-scoped),
  пишет в `config.toml`. Низкоуровневые настройки (лимиты глубины обхода,
  размер батча) в wizard не спрашиваются — разумные дефолты, трогаются
  вручную через TOML только power-юзерами. Запуск в любой момент — это и
  есть путь реконфигурации, отдельного объяснения не требуется.
- **`g-mesh config --global`** (закрывает пробел — раньше не было способа
  настроить глобальный конфиг вообще) — тот же wizard, но скоуплен на
  **глобальный** `~/.g-mesh/config.toml`: спрашивает про
  `cleanup.enabled`/`cleanup.idleThresholdDays` и другие будущие
  кросс-проектные настройки.
- Позже (если появится UI) — тот же сценарий как графический wizard/
  settings-панель. TOML остаётся единственным источником истины в обоих
  случаях — CLI-wizard и будущий UI лишь разные способы его заполнить, не
  разные форматы хранения.

Отдельно от per-project конфига существует **глобальный** `~/.g-mesh/config.toml`
— настройки, применимые до того, как известно, к какому проекту относится
конкретная директория под `~/.g-mesh/projects/`. Первый и пока единственный
кейс — уборка неиспользуемых проектов, см. ниже.

### Уборка неиспользуемых проектов (garbage collection)
Решение: **никакого автоматического удаления по умолчанию** — только
предупреждение. Удаление всегда явное, через отдельные CLI-команды.

Проблема, которую это решает: `~/.g-mesh/projects/<hash>/` не освобождается
сама, когда проект переименован/перенесён/удалён с диска — раньше это было
отмечено как пробел без решения.

Ключевое разделение — не пытаться надёжно определить "путь исчез навсегда"
(сетевой диск может быть просто временно не примонтирован, и удаление по
этому признаку рискует стереть валидный индекс), а полагаться только на
**время простоя**: у каждой записи хранится `lastUsed` (обновляется при
каждом старте демона/обработке запроса для проекта, персистится на диск).

- **Переключатель и порог — в глобальном `~/.g-mesh/config.toml`**:
  `cleanup.enabled` (вкл/выкл сама проверка) и `cleanup.idleThresholdDays`
  (дефолт — 90).
- **Триггер проверки (уточнено — не привязан к lifecycle демона)**:
  сканирование `lastUsed` — дешёвое чтение файлов с диска, для него не
  нужен живой демон. Выполняется самой CLI-командой в момент запуска, а не
  фоновым ядром: **любая интерактивная команда, вызванная человеком**
  (`g-mesh status`, `g-mesh init`, `g-mesh clean`, `g-mesh plugins list` и
  т.п.) — если `cleanup.enabled`, перед обычным выводом печатает
  **предупреждение со списком** (какие проекты, сколько дней простоя).
  Ничего не удаляет автоматически. **Shim-инвокация (спавн MCP-клиентом)
  исключена** — её stdout уходит агенту по MCP, а не человеку в терминал;
  предупреждение туда не печатается. Это гарантирует, что предупреждение
  всплывёт при следующем ручном обращении разработчика к `g-mesh`,
  независимо от того, сколько ядро демона уже работает без перезапуска
  (см. пересмотренный lifecycle в разделе "MCP-транспорт и lifecycle" —
  ядро теперь не перезапускается на idle, поэтому раньше сформулированный
  триггер "при каждом запуске g-mesh" мог вообще не срабатывать).
- **Ручное удаление — явные команды**:
  - `g-mesh clean <project-id>` — почистить кэш конкретного проекта
    (по идентификатору/хэшу).
  - `g-mesh clean` **(без аргументов)** — алиас на `g-mesh clean
    <project-id>` для проекта текущего `cwd` (тот же безопасный,
    осознанно скоуп-ленный случай — `--force` не нужен, как и у явного
    `<project-id>`). Если `cwd` не распознаётся как g-mesh-проект —
    команда завершается ошибкой с просьбой указать `<project-id>` явно, а
    не выбирает что-то произвольно.
  - `g-mesh clean expired` — удалить все записи, просроченные по
    `idleThresholdDays`. Действие уже осознанно ограничено списком
    просроченных — без запроса на `--force`.
  - `g-mesh clean all` — удаляет вообще всё, независимо от простоя.
    Без флага `--force` — только предупреждение ("будет удалено N
    проектов, добавьте `--force` для подтверждения"), без флага ничего не
    удаляется.

Безопасно по построению по той же причине, что и версионирование схемы:
индекс — воспроизводимый локальный кэш, не пользовательские данные,
пересобрать дешевле, чем рисковать случайным удалением того, что ещё
нужно — отсюда и выбор "предупреждать по умолчанию, удалять только по
явной команде", а не автоматическое удаление.

### Версионирование схемы графа
Решение: **полная переиндексация при несовпадении версии схемы**, без
миграционного фреймворка в v1.

- В SQLite хранится `schema_version` (строка в служебной `meta`-таблице).
  При старте core сверяет её со своей ожидаемой версией.
- При несовпадении — не мигрирует данные, а сбрасывает локальный индекс и
  переиндексирует с нуля. Тот же code path, что и обычный холодный старт.

Причина: индекс — локальный воспроизводимый кэш, не пользовательские
данные, пересобрать дешевле, чем писать и поддерживать миграции. Работает и
на апгрейде, и на откате на старую версию (для отката классические миграции
всё равно не помогли бы — down-миграций у нас нет).

Расхождение версий — не экзотика, а обычное "код обновился, данные на диске
отстали": возникает при обновлении core-бинарника, при добавлении новых
типов узлов/рёбер, при появлении нового языкового плагина, требующего новых
полей, при откате версии.

**Когда пересмотреть (не для v1)**:
- Схема графа стабилизировалась (сформировался костяк типов узлов/рёбер,
  изменения стали редкими), но core продолжает выпускаться часто — тогда
  реиндекс на каждый апдейт становится ощутимой болью, а не редким событием.
- Индексы на огромных монорепах начинают занимать неприемлемо много времени
  на полную пересборку (сотни тысяч файлов), и даже быстрый холодный старт
  (tree-sitter-слой) ощутимо бьёт по UX при частых апдейтах core.
- Появляется сценарий, где потеря индекса дорога сама по себе — например,
  если в индексе начнут накапливаться данные, которые невозможно быстро
  пересчитать локально (не наш случай сейчас: сейчас всё выводится
  детерминированно из исходников).

В любом из этих случаев — переход на инкрементальные миграции
(`refinery`/`sqlx migrate` и т.п.), а не раньше.

### Privacy/telemetry-позиция
Решение: жёсткая гарантия "содержимое проекта не покидает машину" отдельно
от разрешённого сетевого доступа самого g-mesh; telemetry отсутствует в v1.

Ключевое разделение — принцип касается **содержимого проекта** (файлы,
символы, эмбеддинги, граф — всё, вычисленное из исходников), а не "вообще
никакой сети".

- **Жёсткая гарантия**: содержимое проекта не передаётся никуда ни в одной
  дефолтной конфигурации, без исключений без явного informed opt-in.
  Уже подкреплено: embedding только локальный (если появится облачный API —
  только explicit opt-in, никогда не дефолт); плагины не получают сетевых
  прав, не нужных для анализа (см. sandboxing); MCP-транспорт — stdio+shim,
  весь трафик локальный.
- **Разрешённое сетевое использование** (не нарушает принцип — это "g-mesh
  качает что-то к себе", не "код уходит наружу"): загрузка бинарников
  плагинов из registry, скачивание весов embedding-модели при установке,
  проверка обновлений core.
- **Telemetry отсутствует в v1** — не opt-out, а вообще не реализована.
  Аудитория индексирует потенциально проприетарный код, доверие критично
  для принятия инструмента. Кандидат на будущее — **opt-in** (дефолт
  выключено), анонимная, без содержимого кода, только при появлении
  конкретной причины (например, нужны crash-репорты для стабилизации).

**Задел на будущее подключение crash-репортов** (не реализовывать в v1, но
учесть при проектировании архитектуры, чтобы не пришлось переделывать):
- Обработка ошибок/паник в core должна идти через единую точку (центральный
  error-handling/logging слой), а не быть разбросана по кодовой базе — тогда
  подключение crash-репортинга (`sentry` и подобные крейты для Rust) позже
  сводится к подключению sink'а к этой точке, а не к рефакторингу.
- Внутреннее представление ошибок не должно по умолчанию встраивать сырой
  текст исходного кода в сообщения/контекст паники — только структурные
  данные (путь к файлу, позиция, тип узла/операции). Так будущий
  crash-репортинг можно будет включить с уверенностью, что содержимое
  проекта не утечёт в payload случайно, без отдельной ретроактивной чистки
  каждого места, где формируются ошибки.
- Опция crash-репортов, если появится, — opt-in через `g-mesh config`
  (см. интерактивный wizard конфига, не `g-mesh init` — тот теперь bootstrap
  без вопросов), не тихий дефолт.

### Обработка синтаксических ошибок при live-редактировании
Уточнение: g-mesh не встроен в редактор, видит только то, что записано на
диск через file watcher — "live-редактирование" означает "файл только что
сохранён посреди правки и временно не парсится целиком", а не "ошибка на
каждое нажатие клавиши".

Решение:
- **tree-sitter (быстрый слой)** — error-tolerant парсер, специально
  спроектирован для этого (тот же класс инструментов, что подсвечивает
  синтаксис в редакторах во время печати). На ошибке не падает, отдаёт
  частичное дерево: сломанный участок — `ERROR`-узел, остальной файл
  парсится нормально. Специальной обработки не требует.
- **Семантический слой (TS compiler API)** — точечный/асинхронный вызов на
  файле с ошибками просто не даёт новых уточнений, пока файл не станет
  валидным, без падений (уже заложено в его асинхронной природе).
- **Стратегия обновления графа — keep-last-good, не replace wholesale**:
  обновляются только узлы/рёбра, чьи границы не пересекаются с
  `ERROR`-регионом нового parse-дерева. Всё, что внутри или "за" сломанным
  участком, не удаляется — остаётся как последнее известное состояние, до
  момента, когда файл снова полностью распарсится и чистый diff подтвердит
  реальное удаление. Причина выбора этой стратегии над "удалить всё и
  вставить по-новой": ложноположительное "символ ещё может существовать" безопаснее
  для агента, чем ложноотрицательное "символа точно нет" — второе может
  привести к деструктивному решению агента на основе артефакта тайминга
  сохранения, а не реального состояния кода.
- **Флаг `hasSyntaxErrors`** на узле `File` — прозрачно сообщает агенту, что
  данные по файлу могут быть унаследованы из прошлого состояния, тот же
  принцип, что и `resolved`/`source` на рёбрах.
- **Raw fallback в ответе MCP-инструмента**: для результатов, помеченных
  `stale`, инструмент возвращает не только структурные данные из графа, но и
  сырое текущее содержимое файла — `rawContent`, — чтобы агент мог
  перепроверить сам, не дожидаясь отдельного вызова. Файл целиком, если он
  небольшой; для больших файлов — фрагмент вокруг последней известной
  позиции символа (± N строк) + `filePath`, чтобы не нарушать уже принятый
  token-budget принцип (пагинация/лимиты MCP-инструментов).

### Инвалидация эмбеддингов при смене embedding-модели
Решение: механизм спроектирован сразу, но **реализуется не весь — для v1
используется только одна фиксированная модель**, смена модели пользователем
не поддерживается. Всё, что ниже про пересчёт/фоновую развёртку — задел на
последующие версии, не требуется к реализации в v1.

Отдельный от версионирования схемы графа механизм (структура узлов/рёбер от
выбора embedding-модели не зависит — страдает только векторная колонка,
полный реиндекс графа не нужен).

**Что закладывается архитектурно уже в v1** (чтобы не потребовалась
переделка схемы при добавлении поддержки смены модели позже):
- У каждой векторной записи — поле `embeddingVersion`; в `meta`-таблице —
  текущая активная версия/идентификатор модели. Даже при единственной
  модели в v1 это поле просто всегда равно текущей версии — но само наличие
  колонки избавляет от миграции схемы, когда смена станет поддерживаемой.

**Механизм для последующих версий** (не реализовывать в v1):
- При смене модели — глобальная версия в `meta` инкрементируется, все
  существующие векторы разом становятся "младше" текущей, без изменения
  каждой записи в момент смены.
- Пересчёт — комбинация фоновой развёртки и приоритета по запросу (тот же
  паттерн, что уже применён для tree-sitter/семантики и графа/эмбеддингов):
  узел с устаревшим `embeddingVersion`, встреченный в `search_code`,
  пересчитывается сразу точечно; остальное досчитывает фоновый воркер
  пачками с троттлингом, батчевыми SQLite-транзакциями.
- `search_code` во время докатки ищет только среди узлов с текущим
  `embeddingVersion` (устаревшие исключаются, не подмешиваются с ложной
  уверенностью — в отличие от `stale`-флага у синтаксических ошибок, здесь
  смешивать пространства векторов нельзя в принципе). Ответ несёт
  `indexCoverage` — общий сигнал о неполноте, а не флаг на каждый результат.

### UI
Решение: **v1 — CLI-only**, никакого GUI/веб-интерфейса. **Приоритет UI —
самый низкий среди всех решений в этом документе.**

Основная ценность продукта доставляется через агента по MCP — человеку не
нужно смотреть на граф глазами, чтобы инструмент работал. Уже решённые
CLI-команды (`g-mesh init`, `g-mesh config`, `g-mesh status`,
`g-mesh reindex`, `g-mesh plugins list`, `g-mesh model fetch`, `g-mesh clean`,
`g-mesh stop`) закрывают весь необходимый набор человеческих сценариев для v1:
bootstrap проекта, настройка, проверка состояния демона/индексации (включая
покрытие эмбеддингов из решения про инвалидацию), получение весов
embedding-модели, ручной контроль.

**Уточнение поведения команд** (ранее упоминались как решённые без
конкретики):
- **`g-mesh reindex`** — cwd-scoped, **полный принудительный реиндекс
  текущего проекта**, тот же code path, что и при несовпадении версии
  схемы ("снести и пересобрать с нуля"), а не просто ускорение автоматической
  докатки "грязных" файлов (та и так происходит сама по staleness-check и
  при пробуждении плагина — команда, дублирующая автоматику, малополезна).
  Эскейп-хэтч для отладки, когда есть подозрение, что индекс врёт.
- **`g-mesh status`** — cwd-scoped, отчёт по текущему проекту: жив ли
  демон-ядро, спит ли плагин или активен, размер очереди "грязных" файлов,
  `indexCoverage`, наличие файлов с `hasSyntaxErrors`. Одна из
  интерактивных команд, под которую попадает GC-warning триггер (см.
  "Уборка неиспользуемых проектов").
- **`g-mesh plugins list`** — листинг установленных плагинов из
  `~/.g-mesh/plugins/<language>/` (глобально, не per-project — плагины не
  привязаны к конкретному проекту): имя языка, версия, статус (бандлен с
  core в v1 / установлен отдельно).
- **`g-mesh model fetch`** — не cwd-scoped (веса per-machine, как и
  `~/.g-mesh/models/`), скачивает веса embedding-модели с закреплённой
  ревизии и проверяет их по закреплённым SHA-256. Прямое следствие
  "разрешённого сетевого использования" выше: это единственное место в
  g-mesh, которое ходит в сеть, и ходит только потому, что команду ввёл
  человек — ни демон, ни `search_code` дотянуться до неё не могут (см.
  `core/src/cli/model.rs`). Без неё установленный из бинарника пользователь
  не может включить `search_code` вообще: shell-скрипт лежит в репозитории,
  которого у него нет. `g-mesh model status` — тот же путь разрешения
  директории, но только отчёт, без сети.
- **`g-mesh stop`** (новое, закрывает пробел) — cwd-scoped, явно
  останавливает ядро демона и процесс плагина для текущего проекта. Прямое
  следствие уже принятого решения "ядро живёт, пока не остановлено явно"
  (см. "MCP-транспорт и lifecycle") — команда для этого явного останова не
  была заведена.

**Второстепенные команды** (не блокируют v1, но заводим сразу, чтобы не
забыть):
- **`g-mesh --help`** — v1, по сути бесплатно (CLI-фреймворк на Rust вроде
  `clap` генерирует автоматически), не отдельная работа.
- **`g-mesh --version`**, **`g-mesh logs`** — не для первой версии,
  добавляются по мере реальной необходимости (например, `logs` — когда
  начнёт не хватать вывода `status` для отладки).

Строить визуальный граф-браузер сейчас — существенный объём инженерной
работы (интерактивная отрисовка, производительность на больших монорепах),
конкурирующий за время с тем, что реально критично для v1 (протокол,
плагин, core). Ценность визуализации — доверие/дебаг, не блокирует основной
use case.

**Кандидат на будущее** (не для v1): lightweight local web UI, поднимаемый
тем же демоном на localhost — не новый сервис, а опциональный HTTP-эндпоинт
у уже работающего процесса. Пригодится для визуального браузера графа и
сводного статуса по нескольким проектам разом (CLI `g-mesh status` по
природе скопирован на текущий проект, демонов по одному на проект — единой
картины по всем сразу CLI не даёт).

**Когда пересмотреть**: если CLI-вывода перестанет хватать для диагностики
сложных проблем индексации, появится явный запрос на визуальное
исследование графа, или число одновременно работающих демонов станет
неудобно отслеживать через отдельные CLI-вызовы.

### Способ установки
Решение: **install-скрипт (`curl | sh`) с бинарниками из GitHub Releases
для v1.** npm-обёртка (`npm install -g g-mesh`, привычнее для целевой
JS/TS-аудитории, паттерн esbuild/swc/Biome) — кандидат на будущее, не
блокирует v1.

Оба способа опираются на одну и ту же базу — предсобранные бинарники под
каждую платформу, прикреплённые к GitHub Release. npm-обёртка (если
понадобится позже) — просто ещё один способ доставить те же артефакты
через `optionalDependencies`, не отдельная архитектура.

- **Архитектурное условие на будущее** (не переделка, а требование к
  релизному пайплайну уже сейчас): бинарники публикуются в GitHub Release
  чётко именованными под каждую платформу по стандартным Rust target
  triples (`g-mesh-x86_64-apple-darwin`, `g-mesh-aarch64-apple-darwin`,
  `g-mesh-x86_64-unknown-linux-gnu`, `g-mesh-x86_64-pc-windows-msvc` и
  т.п.) — тот же набор артефактов переиспользуется без изменений, если
  позже добавится npm-обёртка.
- Плагин (self-contained Node SEA/bun-бинарник) попадает в тот же
  архив/релиз под ту же платформу — не зависит от способа установки.
  Install-скрипт проверяет checksum скачанного бинарника перед установкой.
